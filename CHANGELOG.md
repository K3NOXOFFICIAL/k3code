# Changelog

All notable changes are listed here. Until version 1.0, any release may change the config format, the commands or the on-disk state. Versions follow [semantic versioning](https://semver.org/) from 1.0 on.

## Unreleased

### Added

- **`/learned` (issue #141).** Lists the project's gotchas, auto gotchas and learned notes plus the machine gotchas, preferences and overlays with an id each; `/learned forget <id>` removes one and `/learned purge --yes` clears auto gotchas, learned notes and overlays outside an active experiment.

### Fixed

- **A background sub-agent's "always" answer is stored in the project the sub-agent works in.** The sub-agent asks through its parent session's approval callback, which read the parent's current directory when you answered: after `session.workspace.move` (or the next turn) the allow rule was written to the new project's trusted `.k3code/config.yaml`, and an edit preview was built against the new project's file. The callback now takes the asking loop's own permission state, so the rule and the preview use the child's project.
- **Auto mode lets bash write scratch output to `/tmp`.** `pytest > /tmp/out.txt 2>&1; tail /tmp/out.txt` was refused as "Auto mode writes only inside the project roots", although auto-mode bash runs in the sandbox, whose `/tmp` is a private tmpfs nothing on the host sees (without a usable sandbox the command still asks a person first). A redirect into `/tmp` is now auto-allowed like any other sandboxed command; one that leaves `/tmp` (`/tmp/../x`, a host symlink in `/tmp`), lands under `$HOME` or anywhere else outside the project, and every `write`/`edit` outside it, is refused as before.
- **A quote in a trailing comment no longer stops auto mode.** `npm test  # don't watch` or `grep -rn TODO src  # it's a note` asked a person ("could not be parsed safely") in every mode, auto included, because a quote inside a comment can hide the next line from the checks. A comment that ends the command has no next line to hide (a shell that read the quote as one would only hit an unterminated string and run nothing of that line), so it is now decided like the command without the comment. A quoted comment followed by more lines, or inside a `$(...)` or `bash -c` payload, still asks.
- **The planner of an auto session no longer asks for reads outside the project.** The plan-first planning turn (on by default in auto mode) ran in plan mode, which asks a person for every read outside the project and under `/etc`, so an auto session got approval prompts for reads its own turns refuse without asking (a sibling directory, `/tmp`) or allow (`/etc`, toolchain dirs). The planner now decides those reads as the auto session does: toolchain and system dirs run, anything else is refused with the `/add-dir` hint. It also shares the session's approvals instead of starting without them. Plan mode stays read-only, credential paths stay refused, and a user rule that asks still asks.
- **The model is told where its session works.** No part of the system prompt named the working directory, so the model learned it only from tool output, searched `~` or `/` to orient itself and read unrelated files outside the project (each such read asks, or is refused in auto mode). A new "Session scope" section names the working directory (as `~/…` under home), the git repository root when the session runs in a subdirectory, the `/add-dir` directories, and says to search from the working directory only and to name what it needs outside instead of looking around. A session in `$HOME` (or `/`) is told it has no project: work only on the paths the task names and ask which project otherwise. The section depends only on the session's directories, so it is stable for the whole session and every mode (interactive, headless, plan, sub-agents) carries it; the prompt snapshot is updated.
- **A session started in `$HOME` no longer scans the home directory.** The project scan at session start resolved `~` as the project, walked it on every start, proposed recipes for whatever stacks it met there and keyed learned state to the home directory (fast setup already refused this). It now skips `$HOME` and any directory above it; projects below home are prepared as before.
- **"Don't delete anything" no longer forces a high-risk plan (issue #159).** The scope gate's danger floor matched the word wherever it stood, so "don't delete…", "do not touch production", "without deleting", "fix the typo in the deployment docs" or a classifier reason saying "no credentials involved" forced a high-risk plan (a strong-tier planner call before any work). A danger word is now skipped when a negation precedes it in its clause, and a noun-like one (credentials, secrets, passwords, API keys, deploy, migration, production) in a clause about docs, a README, comments or a typo; action words (delete, `rm -r`, drop table, force push, `reset --hard`) still count next to docs words, and the prompt and the classifier's reason are checked separately.
- **A negation or a docs word elsewhere in the task no longer clears a real danger (follow-up to the entry above).** An independent review showed the first version skipped too much: a negation up to two words back or across a comma ("don't worry, just delete the prod db", "no backup needed: drop table users", "without asking, force push") and deploy/migrate next to any docs word ("deploy to production and update the changelog") lost their high-risk plan. A negation now counts only when it governs the danger word directly ("don't delete", "never force-push", "without deleting"), or a noun-like one through one verb ("do not touch production", "don't commit any secrets"); its reach and a docs mention's both end at a comma, colon, dash or "and"; and only nouns (credentials, secrets, passwords, API keys, production, deployment) are skipped in a docs clause.
- **A directory name cannot inject text into the system prompt's "Session scope".** The working directory, git root and `/add-dir` paths were written between backticks as they are; a name with a backtick or a newline (from an unpacked archive or a cloned repository) could end the quote and add lines the model reads as system instructions. Such a name is now shown JSON-escaped in double quotes; plain names keep their backticks.
- **A session rooted at `$HOME` stops asking for quoted readers and `find` (issue #172).** The read-only home sandbox's `home_read_only` gate rejected any command with a quote or glob, so `grep -rn 'foo bar' notes` or `find . -name '*.py'` asked a person every time at `$HOME`. It now accepts single-quoted literal arguments (single quotes never expand) and double-quoted ones with no `$`, backtick or backslash, and runs `find` without the primaries that execute or write (`-exec`/`-execdir`/`-ok`/`-okdir`/`-delete`/`-fprint*`/`-fls`). Safe because the quoted glob is passed to the program rather than expanded by the shell, so no new path is reached: an unquoted glob or `$` still asks, every tree walker (`grep -r`, `rg`, `ls -R`) stays out of the fast path, and every credential-path refusal (reading `~/.ssh`, `~/.config/git/credentials`, a dot-folder path) is unchanged.
- **`env VAR=x <cmd>` is no longer refused as an environment dump.** The `env-dump` hardline matched a raw `^\s*(?:sudo\s+)?(?:env|printenv)\b`, so `env FOO=1 make test`, `env -u X ls` and `sudo env PATH=x make` were denied in every mode even though `env` there only sets up the wrapped command's environment. The check is now token-based: it refuses a dump only when the normalised argv is still `env`/`printenv` (bare `env`, `env -i`, `env -u X`, `env -S printenv`, a redirect like `env > file` or a pipe like `env | grep`), and lets a wrapped command through to its own checks — `env X=1 rm -rf /` is still refused as the rm rule. Safe because the environment is only printed when nothing is left for `env` to run; every dangerous wrapped command is still vetted by the other hardline checks via `normalize_argv`.
- **`env -S 'FOO=1'` is refused as an environment dump again, and so is `declare -x`.** Since `env VAR=x <cmd>` was let through, the words of `env -S`/`--split-string` were read as the command to run, so `env -S 'FOO=1'`, `env -S -0`, `env -S '-u PATH'`, `env --split-string=X=1` and `nice env -S X=1`, which print the whole environment, passed in every mode, and `env -S 'X=1 -u Y rm -rf ~'` slipped past the rm rule. They are now parsed in place as env's own options and assignments, as GNU env does (an abbreviated long option such as `env --u PATH` too), and an `env` left with nothing to run is a dump. `declare`/`typeset` and `export -n`/`export --` with no name (they list every variable with its value) are refused as well; `compgen -e` lists names only and stays allowed.
- **The hardline list refuses Windows/WSL disk destroyers (issue #169).** Nothing stopped `rm -rf /mnt/c` (a WSL mount of a Windows drive), `cmd.exe /c del /s /q C:\`, `powershell Remove-Item -Recurse -Force C:\`, `Format-Volume`, `format C:` or `diskpart`, so an agent on WSL could wipe the Windows host; in auto mode they ran without asking. `rm` now treats `/mnt/<drive>`, its `Users` tree and `Windows` dir like `/`, and five per-command rules (`win-cmd-recursive-delete`, `win-powershell-recursive-delete`, `win-format-volume`, `win-format-drive`, `win-diskpart`) catch the launcher spellings. Safe because each delete rule fires only on a launcher plus a recursive flag plus a drive-root / `\Users[\<name>]` / `\Windows` target, so a project subfolder delete (`Remove-Item -Recurse .\build`, `rmdir /s /q build`, `rm -rf /mnt/c/Users/<name>/project`) is untouched, and the format/diskpart rules only match the verb as the command being run, not as prose or a filename.
- **The Windows/WSL hardline rules catch the common spellings they missed (issue #169).** `cmd /c del /s /q C:\*.*` and `del /s /q C:\*` (a `\*` or `*.*` wildcard after the target), `powershell -c "rm -r -fo C:\"` and `ri -rec C:\Windows` (PowerShell takes any unambiguous prefix of `-Recurse`, in any case), `Remove-Item C:\* -Recurse` (the flag after the target), the profile named as `%USERPROFILE%`, `$env:USERPROFILE`, `$HOME` or `~`, and `rm -rf "/mnt/c/Program Files"` (also `Program Files (x86)`, `ProgramData`, and `C:\Program Files` through cmd or PowerShell) were let through. Deleting a project subfolder (`Remove-Item -Recurse .\build`, `rmdir /s /q build`, `rm -rf /mnt/c/Users/me/proj/build`) is still allowed.
- **Windows launchers and Windows drives are governed under WSL (issue #169).** A WSL install reaches the Windows host through interop, but the permission engine knew only POSIX interpreters: `powershell.exe`, `pwsh`, `cmd.exe`, `wsl.exe`, `cscript`, `wscript` and `mshta` were treated as ordinary leaf commands, so an "always allow `powershell.exe *`" rule was offered (and could be learned in auto mode) and the hardline never looked at what they were told to run. They now count as launchers everywhere (no `<prefix> *` rule, matched case-insensitively and with or without a Windows executable suffix, so `PowerShell.exe` and `/mnt/c/.../powershell.exe` are covered), and the hardline reads the command line they run, quoted or not (`wsl.exe <command>`, `cmd.exe /c <command>`, `powershell.exe -Command <command>` or Windows PowerShell's positional command), like it does `bash -c`. Separately, `rm -rf` of a Windows drive, its `Users`/`Windows`/`ProgramData`/`Program Files` folder or a `…/Users/<name>` profile is now hardline — for the default `/mnt/<letter>` automount (on any Linux host) and for a custom `automount.root` (the drvfs mounts in `/proc/mounts`).
- **Config overlays get a concurrent control arm where they can (issue #140).** A config ("patch") experiment compared the week before its start with the week after, whatever it changed. One whose every key is read by the session's own build (`context.tool_output_chars`, `memory_chars`, `skill_prompt_limit`, `compact_input_chars` and `autonomy.gate_modes`) now splits sessions 50/50 by the same hash as a prompt overlay. Treatment sessions build their loop, system prompt, compaction and scope gate with the patch; control sessions build without it. The shared config is written only when the overlay is kept. Keys every session shares (`task_tiers`, `router.*`, `learning.rank_threshold`) still use before/after. Each experiment records its design and why, and `/optimizer status` shows both.
- **The optimizer scores turn success, not turn completion (issue #140).** A turn that merely finished counted as a success, even one you undid right away; the replay records said `passed: status == "done"` and the A/B score never read an interrupt, an /undo or a test result. Each turn's outcome is now kept in `decisions.db` (`turn_outcomes`, added to an existing database in place): whether /undo or /retry removed it before your next prompt, whether you stopped it, the exit status of its last test/check command, the goal judge's verdict and `--check` result, and the approvals you denied. A turn passes when it finished, was not undone or stopped, its last test did not fail and the judge did not call it blocked. It waits for a possible /undo until your next prompt, the session's end or an hour, and is not scored meanwhile. The score and the replay gate read this `turn_success_rate`; `turn_completion_rate` stays as a secondary number. `/optimizer status` and `run` show this week's success rate and why turns failed, and a judged experiment shows each arm's success rate.
- **`/learned purge` also clears the project's decisions; `--all` clears every project's and the learned preferences.** The purge removed auto gotchas, learned notes and inactive overlays but left `learning/decisions.db` whole, so the daily distill learned the same preferences again from the decisions it kept. It now deletes this project's rows (those filed under its id and those recorded anywhere in its repository) and says how many. `/learned purge --all --yes` also deletes every project's rows and the learned preferences (`learning/preferences.json` and the auto section of `USER.md`). Both keep accepted gotchas and the lines you wrote in `USER.md`; the help and the confirmation prompt say exactly what each form removes.
- **`/memory` lists the files the prompt actually reads.** It showed only `USER.md` and the root `K3CODE.md` (or `AGENTS.md`), while the prompt also reads `CLAUDE.md`, the instruction files of every directory from the repository root down to the session's, `.k3code/rules/*.md`, `learned.md` and `@imports`. It now lists the loader's own scan (one function serves both, so they cannot drift) in prompt order: each file's size, missing, empty or duplicate ones, the files its `@imports` pulled in, which ones the per-file or total cap cut or left out, and the file `/memory add` and `/memory edit` write to. `k3code memory` shows the same listing.
- **One connectivity monitor for the whole daemon (issue #109).** Each live session ran its own NetWatch: a probe loop and an `nmcli` subprocess every 2 s, so an idle daemon with several sessions open spawned `nmcli` several times every 2 s and probed the same provider endpoints repeatedly. There is now a single NetWatch per gateway process that every session's reliability bundle (and the automation offline-gate) shares; sessions subscribe and unsubscribe their own state forwarder, the instance is reference-counted so its one monitor loop and one `nmcli` poll run only while a session holds it (the idle sweeper releases a session's reference), and a provider URL already registered is not re-added. The offline pause and resume-within-10 s behaviour is unchanged.
- **`sandbox.git_writable` no longer leaves a way to redirect the next git run (issue #101 leftover).** With `sandbox.git_writable: true`, the `.git` root stays writable for git's lock files, so a sandboxed command could still plant a `.git/commondir`, a new `worktrees/<x>` admin dir or a code key (`core.hooksPath`, a `filter`/`diff` driver, an `include`, …) in a `config.worktree` that the next, unsandboxed harness git would follow. k3code now snapshots the writable git metadata before each `git_writable` bash command and, after it, removes exactly what the command added (a new commondir, a new worktree admin dir, or code keys the command wrote into a `config.worktree`), logging what it removed; harness git already runs with hooks and fsmonitor disabled. The scrub only ever removes model-planted, code-running entries, never anything the user's own metadata already held.
- **Background bash jobs and unattended harness commands see `.git` read-only even with `sandbox.git_writable` (follow-up to #101).** The scrub that undoes a planted `.git/commondir`, `worktrees/<x>` admin dir or `config.worktree` code key runs when the bash call returns, but a `background: true` call returns as soon as its job starts, so whatever the job wrote to `.git` afterwards stayed for the next harness git; `/goal` checks, fan-out and ultra test runs and automation shell actions honoured the setting too and were never scrubbed at all. Those now always get the git metadata read-only (none of them needs to write it); a foreground bash call keeps the setting and its scrub.
- **Loading an MCP tool's schema no longer breaks the prompt cache, and it stays loaded (issue #168).** A tool `mcp_tool_search` activated was listed at its registration position, in the middle of the tools array, so every request after it missed the provider's cached prefix; and since the gateway builds a fresh tool registry for each turn and each tier, the activation was gone on the next turn or after an escalation and the model had to search again. Activated tools now follow every other tool in the order they were activated, and the session keeps the list (in its saved meta), so later turns, escalated tiers and a resumed session start with the same tools in the same order.
- **The bash sandbox no longer shows uv's credentials.** It bound all of `~/.local/share/uv` read-only, which includes `credentials/` (`uv auth dir`, index tokens), so a sandboxed command could read them. Only uv's `python/` and `tools/` subdirectories are bound now, each when it exists (the permission engine's toolchain list was narrowed the same way in #366). The read-only `$HOME` view of a session started in `~` masks `credentials/` too, as it masks the other credential stores (a bash read of it already asked first).
- **A PreToolUse hook can no longer approve a test runner onto the host when bubblewrap is unusable.** In an interactive auto-mode session without a working sandbox, `make test`, `pytest`, `npm test` and the other builtin sandbox-only runners fell back to "approve to run it on the host" without `needs_human`, so a hook's `approve` ran the project's code unsandboxed with no prompt (the K3NOX-65 fix covered only auto-allowed commands). That ask is now answered only by a person. Accept-edits is unchanged.
- **The bash sandbox no longer shares `~/.cache` with processes outside it.** It bound your whole `~/.cache` read-write. uv installs by hard-linking from `~/.cache/uv`, so a sandboxed command could rewrite a cached file in place and change code in every environment uv built from it, which runs unsandboxed the next time it is imported (`~/.cache/pre-commit` hooks are the same). It could also read `~/.cache/huggingface/token`. The sandbox now sees a cache of its own at `~/.cache` (`~/.k3code/sandbox-cache`, 0700), and the read-only home view also hides `~/.cache/huggingface` and `~/.config/uv`. Behaviour change: the first build in the sandbox re-downloads what your real cache held (uv wheels, npm, pip, go-build), and the sandbox no longer sees models in `~/.cache/huggingface`.
- **`grep` without ripgrep no longer follows a symlink out of the searched tree (K3NOX-650).** The Python fallback (no `rg` on the host, or a pattern `rg` refuses such as look-around) opened a path through a link, so a link made in the sandbox, to a file or a directory, could return lines of a file outside every root with no prompt. The walk now skips a file whose real path is not where the walk listed it, as rg does without `-L`; a link named as the `path` itself is still searched, since the permission engine decided on it.
- **`read`, `grep` and `glob` ask before they reach a credential file of the home directory that a project root covers (K3NOX-640).** With a root at `$HOME` or above it, or one such as `~/.config` or `~/.local`, a read of uv's `credentials/`, `~/.npmrc`, `~/.config/gh`, `~/.docker` or another credential store the read-only home sandbox hides from bash (`sandbox.HOME_RO_HIDDEN`) was an ordinary in-roots read: it ran in the daemon, outside the sandbox, without a prompt in every mode. That read now asks a person in every mode, yolo and auto included (headless and unattended runs refuse it). With a root at or above `$HOME`, the same holds for any other path in a dot folder of `$HOME`, as for bash: `~/.config/git/credentials`, `~/.cache/huggingface/token`, `~/.bashrc`. Toolchain dirs (`~/.cargo/registry`, uv's pythons, `site-packages`), a project below `$HOME` and a root inside a store's folder (a skill in `~/.claude/skills`) read as before, and a user, project or session read rule still decides. `grep` over `$HOME` (with `include: "*"`, or the Python fallback, which walks hidden files) leaves out the lines of every file in a dot folder there, and no search returns lines from a credential store it was not pointed at.
- **`k3code update` only deletes or switches to directories inside `versions/` (follow-up to #185).** A version name comes from a release tag, the installer's last output line or the `previous` file, and a name that was a path (`..`, a `/`, an absolute path) named a directory outside `versions/`, which the update could delete or point `current` at. A version name must now be one install.sh makes (one path component starting with a digit: `X.Y.Z[-pre]`, `<VERSION>-src.<sha>`) and is checked before any delete or switch: a release tagged otherwise is skipped, an installer that prints anything else fails the update, and a `previous` that names no version is no rollback target.
- **One long line no longer stalls redaction or the failure signature (K3NOX-356).** Four patterns started again at every word start inside a long run of letters, digits, `.`, `-` or `_` and scanned to its end: the `NAME=secret` assignment rule, the JWT rule, the URL finder of the export and debug-dump scrubber, and the path placeholder of a tool failure's signature. The time grew with the square of the line, so a 16 KB tool-error line held the agent loop for most of a minute and a 64 KB one for minutes. Each is now tried once per run: 64 KB takes milliseconds, and the same text is hidden. A name glued to a non-ASCII letter (`éDB_PASSWORD=...`) now hides its value too; a JWT glued to a word whose header holds a nested object is hidden from that object on.
- **The hardline list also refuses deleting main or master on the remote (issue #159).** `git push --delete main`, `git push -d origin master` and the empty-source refspec `git push origin :main` were allowed, in auto mode without asking; they are now denied in every mode as `git-push-delete-main`. Deleting any other branch is unchanged.
- **A force push of a branch whose name contains main or master is no longer hardline-denied (issue #159).** The `git-push-force-main` pattern matched the word anywhere, so `git push --force origin fix/main` or `main-docs` was refused in every mode with no rule able to allow it. It now matches only main/master as a whole ref; force pushes onto main or master stay denied.
- **A webhook says when it did not start a run (issue #159).** Every authenticated `POST /hook/<id>` was answered `202 {"ok": true}` and the run was then dropped (cooldown, rate limit, previous run still going) with only an INFO log. The listener now decides first: `429` with `Retry-After` (seconds) for a cooldown or rate limit, `409` while the previous run is still going, each with a JSON `error` and `reason`; `202` only when the run started.
- **Provider error summaries keep the explanation and never a credential (issue #163).** The router's retry, cooldown and failure details cut a provider error at 160 characters, usually inside the status line and URL before the reason, and nothing scrubbed them although the docstring promised it. They now keep up to 500 characters and pass through the secret scrubber first (prefixed keys, bearer headers, URL query secrets and bare 32+ character tokens become `<redacted>`).
- **`$K3CODE_HOME` and `~/.config/k3code` are owner-only (issue #163).** The session, usage, blocker, artifact and automation databases, the cooldown, halt, trust, onboarding and setup files, the decision log, the debug bundle, the browser profiles and `write_config` on first onboarding created their directory with the umask's mode (0755 under the usual 0022), so other users on the machine could list the home and read every file in it that was not 0600 itself; the env file's directory with the provider keys too. They are now created 0700, a home left 0755 by an older version is made 0700 once at startup when you own it, and `k3code doctor` reports the home's mode (`k3code-home-mode`). A project's `.k3code/` (its config, plans, reports) and a chosen `artifacts.publish_dir` keep the umask as before.
- **The fan-out token cap also stops children that are already running (follow-up to #136).** `autonomy.fanout.max_tokens` (and `/ultracode`'s cap on its fan-out) was checked only before a child started and charged only after it ended, so every running child finished its whole run: with `max_parallel: 3` a fan-out could overshoot the cap by three children's runs. A running child's tokens now count after each of its model calls, and once the cap is crossed the running children are interrupted; their subtasks end as `stopped` with the reason (`token budget exhausted (1200/1000 tokens); stopped while running`), the summary and `Stopped early:` line say so, any partial work stays on the child's branch, and the main model takes the subtask over. A child whose call was already its final answer is not stopped.
- **A `file_change` automation no longer re-triggers itself on its own edits (issue #159).** Files the action wrote while it ran were delivered right after the run and fired it again, for ever; changes whose modification time falls inside the run are now ignored. Prompt and goal actions on event triggers (not cron) also get a default `max_per_hour` of 6 when the policy sets none; `max_per_hour: 0` lifts it.
- **`docs/PUBLIC-RELEASE.md` says the repository is public (issue #165).** It still opened with "The repository is private" and described the switch as still to come. It now says the repository is public, which steps were done, and lists what only the owner can still do or confirm: the GitHub settings (Dependabot, secret scanning, branch protection), the archive, the first release, the clean-up, and the 930 commits since the switch, 345 of which carry a non-noreply address and 155 a `Claude-Session:` trailer.
- **Release assets ship the license notices (issue #165).** The wheel packaged only `src/k3code`, the TUI tarball only `dist/`, and the `k3` binaries came with nothing, so no release file carried k3code's `LICENSE`, `NOTICE` and `LICENSES/` or the licenses of the npm packages and Go modules bundled into it. The wheel now has them under `k3code/` (`core/hatch_build.py`; also when built from the sdist), the TUI tarball has them plus `THIRD_PARTY_NOTICES.txt` for its production npm packages, and a `THIRD_PARTY_NOTICES.txt` release asset covers everything, including the Go modules and runtime linked into `k3` (`scripts/release/third_party_notices.py`, from `tui/package-lock.json` and `go list -deps -json=Module`). A package or module without a license, or a wheel without the files, stops `release.sh`; the full check's `vendor` area builds the wheel and checks them.
- **The TUI model picker searches every provider and knows what each model takes (issue #365).** Typing on its first screen now searches one flat `provider/model` list across all providers (a provider had to be picked first); the model list opens with the cursor on the current model (it reset to the first row); the provider step is skipped when there is only one provider; each row shows the model id it sends and the config `descriptions` text (`model.options` sent the ids but nothing showed them, and never sent the descriptions); and the effort step is offered only for models that take an effort level or whose support is unknown (`model.options` now sends per-model `capabilities`; it was offered for every model). `model.save_key` and `model.disconnect` were stubs that read `provider`/`key` while the TUI sent `slug`/`api_key`: they now store and remove the key in the 0600 env file the setup wizard uses, under the provider block's own variable, and the next turn uses it. A variable the daemon's environment sets, or one another endpoint shares, is refused instead; the key is never echoed.
- **uv credentials are never auto-allowed.** The toolchain read list held all of `~/.local/share/uv`, which includes `credentials/` (`uv auth dir`, index tokens), so an auto-mode `read` or `grep` of it from a project ran in the daemon, outside the sandbox, with no prompt. Only uv's `python/` and `tools/` subdirectories count as toolchain reads now; a read of the credentials directory asks a person in every mode, auto included.
- **A planning turn that produces no plan no longer drops the task.** In auto mode, a strong-tier planner that spent its turns reading and never called `exit_plan` (nor answered with text) ended the turn with "Plan not approved; nothing was executed" and the implicit goal ended unjudged: the task was silently dropped. Below high risk the task now runs directly, with a notice ("The planner produced no plan; running the task directly"); a plan the user refused stays refused. A planner stopped by the loop guard or by repeated tool errors also no longer has its stop notice ("I stopped because I was repeating myself…") approved as the plan the executor must follow.

- **The goal judge no longer counts a test mentioned inside quotes as a test run.** The evidence digest split a bash command line on every `;`, `|` and `&&` with a regex, so `echo "x; pytest"` or `git commit -m "fix; pytest passes"` read as a passing pytest run. It now uses the permission layer's quote-aware parser: only a command at a real command position counts, and a test started in the background (`pytest &`) no longer reads as passed.
- **Edits made with bash or an MCP tool count in the goal judge's evidence.** Only the `write` and `edit` tools counted, so a fix made with `sed -i`, a `>`/`>>` redirect, `tee`, `patch`, `git apply` or a tool such as `apply_patch` or an MCP server's `write_file` read as "Files written/edited: none", and a test run before it read as verifying it. These now count (a test's own output, `/dev/null` and `/tmp` targets do not; read-only commands such as `cat`, `grep ">"` or `sed` without `-i` never count), and an edit and a test in one bash call are ordered as they run.
- **The goal judge of a fanned-out turn sees what the children did.** A turn that fanned out stored only the task and the fan-out's summary, so the judge's evidence said "No test/check command ran this turn" and "Files written/edited: none" for work the children had done and tested. It now gets each merged worker's own tests and edits, the files every merge brought in and the tests run on each merged result, in order, followed by the parent's own tool calls when it finishes a partial fan-out.
- **Auto-continue stops on a judge reply that is not a verdict.** A reply from the completion judge without the JSON verdict counted as "continue", and an implicit goal (auto-continue) ran up to three more unattended turns before anything stopped it. It now ends on the first such reply with a notice ("Auto-continue stopped: the completion judge's reply was not a verdict"); a `/goal` keeps failing open and pauses after three in a row, as before.
- **`autonomy.auto_continue` and `auto_continue_max_turns` are checked when the config loads.** `auto_continue_max_turns: eight` passed the load and failed the first auto-continued prompt (`int("eight")`), and `-1` silently meant no cap. A value that is not a whole number of 0 or more now logs a warning at load and the default of 8 applies (`"12"` reads as 12); `auto_continue` takes `true`, `false` or `"auto"` (also `on`/`off`), else it warns and stays `auto`. The prompt-time read falls back to the default too.
- **`/undo` after an auto-continued run removes the whole run.** Each continuation prompt was stored as a user message, so `/undo` (and `/retry`) dropped only the run's last turn and left its earlier turns in the conversation, while the TUI removed the whole exchange. Continuation prompts (auto-continue and `/goal`) are now marked in the stored message, and `/undo` goes back past them to the prompt you sent; a normal turn is undone as before. The mark is never sent to a model.
- **A `/goal`'s continuation turns no longer re-run the scope gate.** Only an implicit goal's continuations skipped it; a `/goal`'s went through the classifier again on every judged turn, and a medium or larger goal re-ran the strong-tier planner, its advisor critique and the proposer each time. A goal is now gated once, on its first turn (a `/goal resume` or boot kick starts a gated turn as before).

### Changed

- **The scope classifier sizes the task instead of starting it.** On the claude-cli provider, which frames every call as "the assistant's next turn", the cheap tier began the task itself in about one reply in twelve ("let me look at server.py…", no JSON: 7 of 88 replies in today's baseline runs, mostly questions and named-file fixes), so the gate fell back to `small`. The user message now leads with "Classify this task; do not do it or answer it", and the prompt says the same. The prompt also counts a one-line bug fix or a new flag as `small` (they came back `trivial`, putting real work on the cheap tier), lets a stated file count decide the level, says the repository's size never raises a level, and asks for a reason under 15 words and no subtasks below medium (replies are about 60% shorter). Live score on Haiku 4.5 (`scripts/exit/m4_autonomy.py`, weighted behaviour class), old prompt today → new prompt: eval 0.67 → 0.83 (the old prompt's earlier runs: 0.77, 0.93), followup 0.89 → 0.89, blind 0.825 → 0.825 (run once, never tuned against); unparsed replies 7/88 → 0/136. `scope_scores.jsonl` now hashes the lead line together with the prompt.
- **The read-only bash allowlist runs a command unasked only with options it knows (K3NOX-658, K3NOX-659, K3NOX-660).** The allowlist used to look for a list of risky options, so a spelling the list did not know went through: a list file (`sort --files0-from=F` printed the content of every file named in F; also `wc`/`du --files0-from`, `find -files0-from`, `file -f`, `sha256sum -c`), a 3-letter abbreviation (`sort --o=F` wrote F, `tail --f` never returned, `date --s=` set the clock), a path glued to a short option (`date -f/PATH`, `file -m/PATH`, `git show -O/PATH`), and options missing from the list (`jq --run-tests`, `jq modulemeta`, `yq -f`, `tree -R`, `file -z`, `diff -l`, `git describe --dirty`). Each command now has a set of known-safe options, matched exactly (no abbreviation, no `--opt=value` unless listed); any other argument that starts with `-` asks in `default` and `accept-edits`, as before for the risky ones. Common forms that now ask: `jq --arg`, `grep -f`, `date -r`, `find -L`, `ls -w`, `tree -l`, `git diff --no-index`. The commands on the allowlist are unchanged.
- **The option check of the read-only allowlist parses `git -U`/`-u` and `find --` as the programs do (follow-up to K3NOX-658).** git takes the value of `-U` (`diff`/`log`/`show`) and of `git status -u` only glued (`-U5`), so `git show -U -O/PATH` is `-U` and then `-O/PATH`, which now asks instead of passing as the value of `-U`; `find --` ends only the leading options, so `find -- -files0-from F` asks like `find . -files0-from F`.
- **`merge-pr.sh` checks only what a small pull request touches.** It runs the `check.sh` areas the PR's files map to (each complete, never `--quick`) and the full check for a big or risky PR: more than 40 files or 1500 changed lines, a `feat`/feature title, more than one merge commit over `Main`, or a change to `VENDOR.toml`, `install/`, `scripts/ci/` or a lockfile. The label `full-ci` or `merge-pr.sh --full` forces the full check; the first line of the output and the `local-ci` description say which ran and why. [`docs/RELEASING.md`](docs/RELEASING.md) has the rules.
- **Fan-out limits fail safe; headless runs are separate A/B samples (follow-up to #342 and #344).** A fan-out budget that was not a non-negative whole number (`autonomy.fanout.max_tokens: 500k`, `1e6`, `-1`, `null`, `true`) used to mean no token cap; it now falls back to the default of 1,000,000, and `0` stays the only way to say no cap (`max_agents` likewise falls back to 4 per subtask). With `max_parallel` above 1 the reviewer slot was only checked for the worker starting; a worker now starts only while a slot is kept for its own reviewer and for the reviewers of the workers already running, so `max_parallel: 3, max_agents: 4` runs two workers and reviews both instead of discarding two finished workers. Every `k3code -p` run without `--session` now has its own session id (`headless-<8 hex>`) in its usage rows and for the prompt overlay's A/B arm, where all of them used to be one pooled sample; the journal and transcript keep the name `headless`, so `--resume` still finds them.
- **Plan-first spends fewer tokens per planned task.** Three calls that ran on every medium-or-larger task in auto mode are gone or narrowed. The proposer no longer runs on the approved plan (its suggestions were deduplicated against the post-task pass anyway); one pass runs after the task, as before. The strong-tier critique after plan approval (`autonomy.advisor_on_plan`) now runs only for a large or huge scope or a high-risk verdict; a medium plan is approved and run as is. The planning turn no longer gets the whole message history as messages (every earlier tool result in full): it gets the same condensed transcript the advisor gets, with long messages clipped and the old part summarized on the cheap tier once the transcript passes `autonomy.advisor_compact_chars` (default 24000 characters). The README documents these keys.
- **Headless runs give up (issue #108).** `k3code -p` waited for ever when the network was down or every provider failed, and said nothing at the default log level, so a cron job hung until something killed it. It now says on stderr when it pauses or parks (`[k3code] parked: ...; next try in 30s`) and waits at most `--max-wait` seconds (default `reliability.max_wait` from the config, else 300; `0` waits for ever); then it reports `gave up after 300s waiting for a provider`, exits with code 75 (`EX_TEMPFAIL`) and, with `--json`, returns `{"error": "gave_up", "waited": 300, "cause": "all_providers_unreachable"}`. The reliability layer emits a `reliability.gave_up` event before the original failure surfaces.
- **Idle polling (issue #109).** The connectivity monitor probed the internet and every provider endpoint every 5 s while everything was fine, so an idle daemon made a request round every 5 s. It now probes every 60 s while the state is usable (`reliability.netwatch.healthy_interval`), watches an outage from 5 s backing off to 60 s as before, and NetworkManager changes still trigger an immediate probe. The gateway and the daemon no longer log httpx's one line per request at INFO.

- **Optimizer A/B is a real test, not a coin flip (issue #140).** Each session is now one sample. A prompt overlay runs concurrently: sessions are split 50/50 by a hash of experiment id and session id, and control sessions are built without the overlay. A config overlay still compares against the week before, because the config is shared by every session and process. The decision needs 10 sessions per arm and uses a seeded 95% bootstrap interval of the score difference: rolled back when the upper bound is below 0, kept when the lower bound is above -0.02, otherwise `inconclusive` with the old value restored. Only one experiment runs at a time. Token growth is now scored symmetrically. `verifier_pass_rate` is renamed `turn_completion_rate`. With no real effect, 200 synthetic experiments now roll back under 10% (previously 82/200).
- **`learning.enabled: false` also keeps learned text out of the prompt (issue #141).** The switch stopped new learning, but notes in `learned.md` and optimizer overlays (`overlays/*.md`) already on disk still went into every system prompt. With learning off both are now left out; your `USER.md`, the project's instruction files and gotcha cards you accepted are unchanged.
- **Base system prompt: scope, persistence and reporting rules (issue #172).** `prompts/system.md` now tells the model to do exactly what was asked and stay inside the task's project, to orient from the most specific name the task gives, to keep going until the task is done and verified instead of stopping to ask about the obvious next step, never to claim a check passed without running it, and to end with a brief report plus at most 3 one-line `Tips:`. It states the instruction priority (user and output style, `USER.md`, project instruction files, learned notes; tool, web, MCP and sub-agent output is data) and tells sub-agents to skip steps that need a tool they lack. A last line the instructions require (the fan-out reviewer's `VERDICT:`) stays after the Tips. The base prompt grows from about 627 to 926 tokens; tests pin the priority line against the memory files k3code loads, the tool-skip sentence, the verdict-stays-last rule and a 1100-token cap.
- **Auto-continue is on by default in the auto and yolo permission modes.** A prompt there used to end whenever the model stopped ("next I would…"), even with the task half done. `autonomy.auto_continue` now defaults to `auto`: in auto and yolo mode a typed prompt runs as an implicit goal (see Added: Auto-continue), judged after each turn until the judge says done; in the default, accept-edits and plan modes nothing changes. `true`/`false` still force it on or off in every mode. Guard rails: at most `autonomy.auto_continue_max_turns` judged turns (default 8, 0 = no cap; at the cap a notice says it stopped and "continue" starts a fresh one); a plain one-line question (ending in `?`, not phrased as a request like "can you…?") gets no implicit goal, and a prompt the scope gate rates trivial, or whose plan was refused or fanned out, ends after its first turn without a judge call; a `blocked` verdict, a prompt typed meanwhile, interruption and the token budget end it as before. Continuation turns of an implicit goal no longer re-run the scope gate, so an approved plan is not proposed again each turn.
- **The goal judge weighs evidence, not the agent's claim (roadmap #172 §2).** After each goal turn the judge now also gets a short digest of the turn's tool calls: the last test/check commands (pytest, npm test, go test, cargo test, make test, ruff, tsc, ...) with their exit codes and whether they ran after the last edit, the files written or edited, and tool errors no later call of the same tool and path resolved; a turn with no such command says so. The digest is fenced as untrusted data. For a code goal, `done` now needs a passing test/check after the last edit or a configured `--check`; a failing last test or an unresolved error means continue. Questions and research are still judged on the answer. Judge failures stay fail-open. A test/check counts only at command position (`cat pytest.ini`, `pip install pytest` and `which tsc` run none), and one whose exit status a pipe, `|| true` or `;` sets is reported as not the test's own. The goal's last check carries across its turns with the files edited since, so a turn that runs no test still shows the judge the earlier result, and a continuation now tells the agent the judge's reason. The `--check configured` note sits in the judge prompt, outside the untrusted digest.
- **Turn-replay records stay small (issue #171).** With `learning.optimizer.enabled`, every turn's record in `learning/replay/turns.jsonl` held a size entry for every message of the whole session, so a session wrote O(N²) and a long one hit the 200 000-character record cap and stopped being recorded. A record now holds the sizes of the turn's own messages and a constant-size summary of the earlier history (its character count and its 16 largest tool results, the only ones a clip candidate can change). Replay totals are unchanged while the history holds at most 16 tool results; past that the optimizer sees a smaller reduction for a clip candidate, never a larger one. Records in the old format still replay.
- **`/settings` shows the saved theme.** The Theme row read the gateway skin name, so after choosing `light` and relaunching it showed `default`. It now reads the `display.tui_theme` pin that `/theme` writes, and cycles `auto`, `light`, `dark` (`default` was never a value `/theme` accepts).
- **TUI README hotkeys.** `Ctrl+L` is documented as a full repaint (same as `/redraw`), not a new session, and `PgUp`/`PgDn`/`Shift+Up`/`Shift+Down` as transcript scrolling; `Home`/`End` are said not to scroll it. A test pins the three rows.
- **System prompt no longer overpromises.** It said `read`, `grep` and `glob` never need permission and that a file you read is unchanged unless you edited it. Reads outside the project ask first and credential paths are refused, and a file can change under a `bash` formatter, `git checkout` or generator, so the prompt now says to re-read after such a command or a failed `edit` match, and to take the reversible option when nobody can answer.
- **`learning` output style in unattended runs.** The `learning` style told the model to leave a `TODO(human)` for the user to implement; in a background or `/goal` turn and in every sub-agent nobody could fill it in. Those prompts now keep the teaching part and tell the model to implement all of it. Interactive sessions and custom style files are unchanged. (#166)
- **Three unreachable TUI overlays are gone.** The skills hub, plugins hub and journey screens (about 1,360 lines) were never opened by any key or command and called gateway methods that do not exist (`skills.manage`, `plugins.manage`, `learning.*`). A test now fails if the TUI source asks for one of those methods or brings the overlay state back.
- **Config writes are atomic.** `config.yaml` (and every other file written through `confio.write_yaml`, plus `/model chain` edits) is written to a temporary file, fsynced and renamed into place, so a crash or a full disk in the middle keeps the old file instead of leaving an empty or half-written one. `/model chain` edits and `/tune --global` take a lock (`.config.yaml.lock` beside the file; best effort, none on Windows), so two concurrent edits no longer lose one of the changes.
- **`NO_COLOR` is honoured in the TUI.** With `NO_COLOR` set to a non-empty value the TUI no longer emits foreground or background colour (it used to produce the same 256-colour output); bold, dim and inverse stay, and the search-match highlight keeps inverse, bold and underline without its yellow. A monochrome / high-contrast theme is not part of this change (issue #170).
- **Idle TUI no longer repaints every second.** The status line's session clock and the `✓` time since the last answer ticked once a second even with nothing running (about two frames a second, ~35-70 bytes/s on a quiet session). They now show whole minutes (`<1m`, `5m`, `1h 2m`) and repaint once a minute, on the minute boundary. The running turn's clock (`· 12s`) still counts seconds. (#170)
- **Path completion no longer stalls the gateway.** `complete.path` reads the directory on a worker thread, looks at no more than 2000 entries and sorts only the matches, so Tab on a huge directory does not freeze other sessions; the TUI no longer asks it to complete words containing `://`.
- **`write` and `edit` into a locked file, read-only directory or bind mount.** When the temp-file rename is refused (`EACCES`, `EPERM`, `EBUSY`, `EXDEV`) and the file exists, the file is now rewritten in place (old bytes kept in memory and put back if that write fails) instead of failing with `PermissionError`. A full disk (`ENOSPC`) never takes this path, and the atomic temp-file write stays the default. Run as root, the atomic path now also keeps the original file's owner.
- **Answers files are checked.** `k3code setup --non-interactive --answers` and `k3code onboard --answers` now reject, before anything is written, a file that is empty or not a mapping, not valid YAML, has a key that no step reads (a typo such as `onboard.provder` used to configure the default provider and exit 0), holds a value of the wrong type, or answers a menu with something that is not on it (`permissions.mode: yoloo` used to be written to `config.yaml` and stop every later start; `usage.primary: foo` was a `KeyError` traceback). A provider entry needs a base URL (or a preset that has one) and an `api_key_env` that is a variable name. Yes/no answers must be `true` or `false` (a quoted `"false"` used to count as true and installed the systemd unit). The error is one line naming the file and the key, with exit code 2; `install/answers.sample.yaml` documents every section, including `onboard:`.
- **Parallel reads.** Consecutive read-only tool calls in one model reply (`read`, `grep`, `glob` and the like, never `bash`) now run at the same time instead of one after another. Any other call waits for the ones before it, a batch that would need an approval prompt runs in order, and results reach the model in the order it asked.
- **Invalid tool-call blocks.** With the `claude-cli` provider, a `<tool_calls>` block that is not valid JSON no longer fails the whole model call and triggers a full retry. Trailing commas, `True`/`False`/`None` and a missing final `]` are repaired; anything else reaches the model as an error result ("Your `<tool_calls>` block was not valid JSON ...") so it can re-send the calls. A block that is opened but never closed is still a provider error.
- **Faster local CI.** `scripts/ci/check.sh` runs the core test suite in parallel with `pytest-xdist` (a new dev dependency; 8 workers or the CPU count if lower, `K3CODE_CI_PYTEST_WORKERS` to change it), then runs the tests marked `serial` (the ones on the host's real systemd programs and the two that use a pty as the controlling terminal) alone. A full run of the suite drops from about 5 minutes to under a minute. Plain `uv run pytest -q` still runs everything in one process.
- **CI runs locally; no GitHub Actions.** The workflows `ci.yml`, `gitleaks.yml`, `installer.yml` and `release.yml` are removed. `scripts/ci/check.sh` runs the same checks on your machine (core, tui, panes, vendor, secrets, plus shellcheck of the shell scripts), with `--quick`, `--changed` and `--only`; `--post` sets the `local-ci` commit status that branch protection on `Main` requires. `scripts/ci/merge-pr.sh` merges a pull request after a full check of its merge with `Main`, `scripts/release/release.sh` builds and publishes a release (the assets of `release.yml` plus the hashed `k3code-<version>-requirements.txt`), and `scripts/dev/install-hooks.sh` installs a pre-commit and a pre-push hook. `scripts/ci/platforms.sh` replaces `installer.yml` as far as Linux can: it installs, updates, rolls back and uninstalls in clean Ubuntu 24.04 and 22.04 (no Go: `--full` checks that the installer fetches its own), Debian 12, Fedora 44 and Alpine 3.20 containers and through `install.ps1` against a WSL stand-in, and reports each step's time. See [`docs/RELEASING.md`](docs/RELEASING.md).
- **A main-tier turn that stalls continues on the strong tier.** After `autonomy.max_tool_errors` (default 8) failed tool calls in a row, or a loop-guard stop, a turn that started on `main` no longer stops and asks: the strong tier continues it with the conversation so far, and the session shows `escalated interactive_turn: main → strong (...)`. Only a stall on strong ends the turn with the list of failed calls and asks for input. Goal continuations and background turns that run on `main` climb the same way; `autonomy.escalate_main: false` keeps the old stop.
- **Look.** The default theme is hot pink (deep pink, hot pink, violet-red rules, plum fills; darker raspberry on a light terminal). Errors, success, warnings and shell mode keep their own colours. Turns are separated by a full-width rule, the status line is one continuous rule between the conversation and the input, and the agent list has a labelled header (`agents (N) · ← agent view`).
- **Agents.** The agent list under the input is read-only: ↑/↓ always walk your previous inputs and never move into it. ← on an empty prompt opens the agent view, which groups sessions and sub-agents into Needs input, Working and Completed (earlier sessions of the project, dimmed, at the end of Completed) and opens on the current session; ↑/↓ select, → or Enter attaches (on a sub-agent: its live view, Esc goes back), x stops (asks first), n starts a new session, ← or Esc goes back. Finished agents leave the list after a minute.
- **Tool output.** `bash`, `grep` and `glob` results reach the model and the screen as plain text (stdout as it is; stderr, an error note and a non-zero exit code only when there is something to say), not as the Python repr of a dict with every newline and quote escaped. `write`, `edit` and plain errors are one line too (`Wrote /path`, `Edited: 1 replacement`, `Error: File not found: x`).
- **Stored sessions.** At start the daemon deletes stored sessions that never got a message, have no title or per-session setting, are not live or referenced by any loop or automation (paused ones included), and were last touched more than 30 days ago. Every `k3code agents`, `n` and abandoned TUI start used to leave one behind for good.
- **claude-cli streams.** The `claude-cli` provider shows the reply as it is written (`--output-format stream-json`) instead of all at once after several seconds; the `<tool_calls>` block never reaches the screen. It passes `/effort` on as `--effort` (a provider entry's new `effort` field is the default), and its usage records cache reads and writes.
- **claude-cli keeps its process.** The `claude-cli` provider keeps a live `claude -p` process per conversation and sends each step only the new tool results and messages, so the CLI start is paid once and the prompt cache covers the earlier conversation instead of writing it again every step. Any change to the earlier conversation (compaction, a retry, another provider's answer) starts a fresh process with the whole conversation, and a failed step kills its process. New provider entry fields: `persistent` (default true; false keeps one stateless call per step), `max_sessions` (default 4) and `idle_seconds` (default 600).
- **`/help`** lists the gateway's commands by category (it showed only the TUI's own commands).
- **Logging.** `k3code -p` prints only warnings by default, ends the answer with a newline and says why on stderr when a run fails. `K3CODE_LOG_LEVEL=info` brings the log back.
- **Rejected keys.** A provider entry whose key is rejected (401/403) twice in a row now cools down for 5 minutes, doubling per further rejection up to 1 hour (one stray rejection arms nothing, and an entry with no key, such as `claude-cli`, never cools down), so later calls skip it at once instead of posting to it and probing `/models` on every step. The cooldown belongs to the key that was rejected: a replaced key is tried immediately, `k3code doctor` clears it when the key answers, and `k3code onboard` / `k3code setup` clear it after writing a provider. When every entry is rejected the error says authentication failed (and points at `k3code doctor`) instead of "rate-limited until".
- **Usage timings.** The `call` and `tool` rows in `usage.db` now record their wall time in `seconds` (a model call from its first attempt, failovers included, to its answer; a tool from the end of the model message or the previous tool to its result), in the daemon, in `k3code -p` and for side calls such as titles and compaction. They were always 0, so `k3code stats` could not show where time goes.
- **No step limit by default.** `max_turns` (model calls per prompt) defaults to 0, no cap (it was 20). A configured cap that is reached no longer ends the turn silently as if the task were done: the turn ends as needs input with a message saying it stopped after N model calls, an active goal pauses instead of being judged, and `k3code -p` exits 1 with the reason on stderr. Sub-agents are the exception: nobody watches them, so with no global cap they stop after `subagents.max_turns` model calls (default 200; a smaller positive `max_turns` wins) and after `autonomy.max_tool_errors` failed tool calls in a row, and the result they hand the parent says why. Unattended runs (`k3code -p`, automations, background goals) get no separate default cap either (issue #49): a model that keeps making successful tool calls, never repeating one, can spend tokens until the run ends, so set `max_turns` or a `reliability.session_tokens` / `reliability.session_usd` budget for a run nobody watches. Repeated identical calls are still stopped by the loop guard and `autonomy.max_tool_errors` failures in a row end the turn.
- **Goals run until done.** `goal.max_turns` defaults to 0, no turn budget (it was 300), and a failing `--check` pauses the goal after 20 failed checks instead of 3 (new `goal.gate_max_retries`, default 20, settable with `/config`; 0 = no limit, `/goal resume` starts the count again), so a check that can never pass (a typo, a missing tool) cannot burn tokens until someone looks (issue #49). The goal still pauses sooner when it is judged blocked. The status line and notices read `12 turns` / `turn 12` without a budget. `/goal --turns N` still sets one (`--turns 0` = none), and `/goal resume` keeps the budget a goal was stored with, so a goal set before this change keeps its 300.
- **`release.sh` refuses an unfolded changelog.** The release notes are the `## [X.Y.Z]` section of `CHANGELOG.md` alone, so `scripts/release/release.sh` (and `--dry-run`, which reports it) now refuses while `## Unreleased` still holds entries, instead of publishing notes that leave them out. [`docs/RELEASING.md`](docs/RELEASING.md) says to rename `## Unreleased` to `## [X.Y.Z] - <date>` and start a fresh, empty one.

- **First-run guidance.** Every no-provider hint names `k3code onboard`: `k3code doctor` no longer says to edit `config.yaml` by hand, and the TUI Setup Required panel drops its dashboard and Desktop text and points at `k3code onboard` instead of `k3code setup`. `/setup` in the TUI now starts `k3code onboard` (fast by default); `/setup --step NAME` still runs the wizard.

- **Setup.** Fast setup over an existing config puts the new provider first and keeps the others as fallbacks. `k3code doctor` reports a provider without a key as a warning while another provider can still answer.
- **`/model`, `/effort` and bare `/ultracode`.** `/model` and `/effort` now run through the same code as `/tune`; their arguments and replies are unchanged. A bare `/ultracode` used to print a usage line and now flips the ultracode mode. `model.options` reports the model key of the session asked about, not only `default_model`.
- **`glob` and `grep` are bounded.** `glob` and the grep fallback skip `.git`, `node_modules`, virtualenvs and tool caches the way ripgrep does (also inside a git work tree), stop at 1000 results and after a 10 s wall-clock budget, and say so with a hint to narrow the pattern or pass a smaller path. A search of the home directory used to walk everything and ran for minutes.
- **`bash` at the home directory asks.** The bash sandbox refuses to bind `$HOME` (or a directory above it) writable, so an interactive `auto` or `yolo` session started there had every `bash` call refused. It now asks for each command and runs the approved one without the sandbox. Unattended runs (background, goal continuations, sub-agents) stay refused, with a hint to start in a project directory. With no usable bubblewrap nothing is asked, as before: `bash` already runs unsandboxed there.
- **Prompt caching behind relays.** A Claude model id sent through an OpenAI-compatible endpoint other than `api.openai.com` (OpenRouter, LiteLLM, OmniRoute) now carries Anthropic's `cache_control`, so the prompt cache applies instead of every turn paying for the whole prompt again. `prompt_cache: auto` (the default) guesses this; a relay that rejects the field turns the marking off for the rest of the run, and `prompt_cache: on` or `off` on a provider entry overrides the guess.
- **Prompt caching for gateway aliases.** `prompt_cache: on` on an OpenAI-compatible provider entry now sends cache breakpoints for every model id, so an alias such as `auto/coding-manual` in front of Claude is cached too (it was sent only for ids containing `claude`). `prompt_cache: auto` keeps the Claude-id rule, and the new `cache_models: [glob, ...]` on a provider entry opts further ids in under `auto`. `k3code doctor` names the alias ids that `auto` leaves uncached and how to turn caching on.
- **A leaner system prompt.** The prompt tells the model to run independent read-only calls in parallel and to take fewer, bigger steps; it shrank from about 2.3k to about 1.5k tokens, and it names 30 skills (was 60), the rest staying reachable through the `skill` tool.

### Added

- **`/provider` switches between the configured providers.** A bare `/provider` lists the provider blocks from `config.yaml` and marks the active one. `/provider <name>` makes the session's turns try that block first from the next turn on; the other blocks stay behind it as the fallback, and the transcript is kept. An unknown name is refused with the valid names. `--save` also writes it as `default_provider` to the user `config.yaml` (validated and backed up, like `/tune --global`), which new sessions then start on. In the gateway and the TUI, with `/help` and command completion.
- **`k3code prompt dump`** prints the system prompt as a mode would start it (`--mode interactive|headless|plan|subagent:<type>`), with `--sections` for a per-section size table (chars and estimated tokens), `--tools` for the tool schemas and `--hash` for its SHA-256. `/debug dump` bundles now hold a `prompt.json` with a short hash and the section sizes of every mode, never the text. `k3code -p`, the REPL and the daemon read the base prompt through one loader (`prompting.base_prompt`; there were three copies), and `core/tests/snapshots/prompt_hashes.json` pins the assembled prompt of each mode: a change to `system.md`, a sub-agent type or the plan addendum fails `tests/test_prompt_dump.py` until `K3CODE_UPDATE_SNAPSHOTS=1 uv run pytest tests/test_prompt_dump.py` rewrites it (GitHub #166, finding 2).
- **Decision model for context (optional, off by default).** With `context.decision_model.enabled: true`, a small, cheap model reads the old tool results a long turn is about to drop from the request and decides per result: keep it whole, or drop it and keep a short note of the facts that still matter (paths, line numbers, values, errors). The main model gets fewer input tokens without losing what it is working with. It runs only where old results are dropped anyway (in batches), so it adds no prompt-cache misses, and any failure falls back to plain dropping. It uses the cheap tier (`task_tiers.context_select` picks another), or a named model: `model: <id>` and optionally `provider: <provider block name>`. `at_ratio` (default 0.5) sets the share of the context window at which it starts; an invalid setting turns it off with a warning.
- **Self-verified gotchas apply on their own.** A tool failure that came back twice in a project within 14 days, and whose retry worked (for example `npm install --legacy-peer-deps` after a failed `npm install`), is noted for the in-turn reminders on its own (in `gotchas.auto.md` next to the project's `gotchas.md`) and proposed as a project-gotcha card at the same time; the session gets a one-line notification saying it was noted and can be promoted. A noted line is tool output plus the model's retry, so it never goes into the system prompt: only an accepted card puts it there. It is learned once per signature. A failure without a working retry still waits for the third sighting and the card. Denials, invalid arguments and hints the scrubber redacted something in are never learned this way. Set `learning.auto_gotchas: false` to keep the card for every gotcha.
- **Auto-continue.** With `autonomy.auto_continue` on an ordinary prompt typed in a session runs like a `/goal` of its own: after each turn the cheap judge reads the reply, and while it says continue a continuation prompt starts the next turn, so a model that stops early ("next I would…") carries on until the judge calls it done or blocked. A chat reply counts as done once it is answered, so it costs one judge call and no extra turn (a plain question costs none: see Changed). The goal snapshot carries `implicit: true` for it, and the goal bar labels it `↻ auto goal`. It ends cleared, never paused: done, blocked, interrupted, needs input, halted or failed, there is no "Goal paused… /goal resume" notice, the daemon never restarts it, and the next prompt or a `/goal` replaces it. A `/goal` that is active or paused is left alone. Background, cron, loop and automation turns, sub-agents and `k3code -p` never auto-continue. On by default in the auto and yolo permission modes (see Changed).
- **A known fix is shown when the failure comes back.** When a tool call fails in a way the project already has a lesson for (a known pitfall, or a retry that worked within the last 14 days), the model gets a one-line `[learned]` reminder right after the step's tool results that quotes the recorded failure and the retry that worked as data (« », not an instruction), once per failure per turn and next to the loop guard's own reminder. The system prompt is not changed mid-turn. A pitfall accepted from a card in two or more projects (never a line only noted automatically) is also kept in `$K3CODE_HOME/gotchas.md` and shown in the system prompt as "Known pitfalls on this machine", and its reminder reaches every project.
- **`/tune`: model, effort and ultracode in one popup.** In the TUI `/tune` opens one screen: `↑`/`↓` pick the model, `←`/`→` the reasoning effort (`default`, `low`, `medium`, `high`, `xhigh`, `max`), `Tab` the ultracode mode, `Enter` applies it and makes the highlighted model the default for new sessions (`s` leaves the default alone), `s` applies it to this session only, `Esc` cancels. A bare `/model` and a bare `/effort` open the same popup. Typed, `/tune [model <key>|<key>] [effort <level>|<level>] [ultracode [on|off]] [--global]` takes the words in any order, checks all of them first and applies all or nothing; an unknown word is an error and changes nothing. The old picker's spellings still parse (`--reasoning <level>`, `minimal`/`ultra`/`none` after `effort`, `--provider`, `--tui-session`). `/model <key>`, `/model chain` and `/effort <level>` keep working and say what they said, and `/model <key>` takes `--reasoning` and `--global` too. New RPCs `tune.get` and `tune.set` serve the popup (`tune.set` is refused in a read-only attach, as `config.set` is; a provider that does not define a key contributes its default model to a row's `providers` and `resolved`) (one row per model key with the model ids it resolves to, whether the model takes an effort level, and an optional description from the new `descriptions: {key: text}` on a provider). The popup fits 80x24, drops the descriptions below 70 columns, and stays closed while an approval, question, password or confirm prompt is open. `/help` lists `tune` under "Model and settings".
- **The default model is saved.** `/tune ... --global`, `/model <key> --global` and `Enter` in the popup write `default_model` into the user `config.yaml`; before, a model switch without a session changed the default in memory only and a restart lost it. The write follows `/model chain`: the key must exist, the result is validated, a timestamped backup is made, then the file is written. A failed write is reported and applies nothing else from that request. Only the user config is written, never the project's. The rewrite does not keep YAML comments; the backup does.
- **Ultracode mode.** `/ultracode` with no argument flips a per-session mode, `/ultracode on`, `/ultracode off` and `Tab` in the popup set it, `/ultracode status` reports it, and the status line shows an `ultracode` chip while it is on. With the mode on, a prompt you type runs the ultracode pipeline when the plan-first scope classifier rates it at least `ultracode.min_scope` (default `small`, so everything except `trivial`); `trivial` prompts and a classifier failure run as a normal turn. The mode skips slash commands, text the TUI generated, a prompt with an approved plan (`/go` after `/ultraplan`) and background sessions. It is kept with the session, restored on resume and inherited by `/fork`, `/branch` and background sessions; `session.info` carries `ultra_mode`. `/ultracode <task>` is still a one-shot run and does not change the mode.
- **Wake words.** Typing `ultracode`, `ultraplan` or `ultraresearch` in a prompt runs that mode once on Enter, with the word removed from the task (your own text stays in the transcript). A word counts only when it stands alone: not in a slash command, a path, a flag, an `@mention` or a `#tag`, not quoted or in code, and not when the prompt names two different wake words. A prompt that is only the word gets the command's usage line, and the composer paints a word that counts in the accent colour while you type. `ultra.progress` reports the phases `wake word` and `ultracode is on` first. Typed `ultracode on|off|status` (also "turn off ultracode") sets or shows the mode instead of running. `UserPromptSubmit` hooks run before a wake word or the mode routes a prompt, so a blocked prompt reaches no model, and a hook's context goes to the run. Detection is linear in the prompt length. Quote or backtick the word to say it without running anything, or set `wake_words.enabled: false` (or `wake_words.ultraplan: false` and so on per word). Wake words do not apply to `k3code -p` or the line REPL. Security: only text you typed is checked (a sent prompt, a queued or steering prompt when it runs, `/bg <prompt>`), so tool output, goal prompts, loop, cron and automation ticks, sub-agents and anything the TUI generated (`/skill` expansions, the `/go` send, an accepted proposal) cannot start a multi-agent run. `prompt.submit` and `session.steer` take an `automated` flag for that; the TUI sets it on the prompts it generates.
- **Project recipes.** k3code detects every stack of a project, monorepos included (Python, Node/Deno, Go, Rust, Nix, Docker, Home Assistant, Java, Ruby, PHP, Terraform, Ansible, .NET, Make/just, CI), with the test, lint, format and build commands read from its files (nothing is run). The result is kept in `$K3CODE_HOME/projects/<project>/project.json`, not in the repository, and a changed marker file triggers a re-scan that proposes only what is new. Each stack offers opt-in proposal cards: matching skills to pin, an MCP server (a docs server; for Home Assistant its MCP endpoint, with the token named by `HASS_TOKEN`), a formatter hook after edits, exact-command allow rules for its test and lint commands, and its commands to confirm. Accepted rules, MCP servers and hooks apply to that project only. The system prompt gets a short "Project facts" section, the skills index lists the project's matching skills first, `k3code setup`/`onboard` offers the recipes (`project_recipes: accept_all|none|ask` in an answers file) and `/project` shows the stacks and pending proposals (`/project rescan` re-scans).
- **Background bash.** `bash` takes `background: true`: the command goes through the same permission decision and sandbox as any `bash` call and returns a `job_id` at once. `bash_output` returns what the job printed since the last read and whether it still runs; `bash_kill` stops its process group. Both are allowed without a prompt and reach only jobs of the calling session; a session's jobs are killed when the gateway closes it or shuts down, a sub-agent's when it finishes, and a `k3code -p` run's or REPL's when it exits. The `bash` schema documents its timeout (default 30 s, max 600 s), and a timeout says how to go on.
- **Learning from tool errors.** Tool arguments are checked against the tool's schema before the call (and before any approval prompt): the model is told what is missing or wrong and what the tool expects, instead of `Tool execution failed: 'path'`. A failure that recurs in a project (3 times in 14 days) is proposed as a project gotcha; accepted ones are kept in `$K3CODE_HOME/projects/<id>/gotchas.md` (never in the repository) and shown to the model as known pitfalls. The reason typed with a denial is kept (scrubbed), and two similar reasons for the same command become a preference proposal.
- **Loop guard on results.** The same failure three calls in a row (whatever the arguments) or two calls alternating over six calls gets one specific reminder; a turn on the top tier it may reach stops after `autonomy.max_tool_errors` (default 8) failed calls in a row and lists them (a main-tier turn first continues on strong, see above).

- **Agent view.** `←` on an empty input, `/agents` or `k3code agents` (on the daemon) opens a full-screen list of every session and sub-agent by state, plus earlier sessions of the current project; `session.list` rows now carry the session's `cwd`, and a `cwd` param filters the list to that project on the gateway.
- **`sandbox.home_readonly`** (user config only): `$HOME` entries that stay visible, read-only, inside the bash sandbox, for example `[".myapp"]`. The sandbox hid all of `$HOME`, so a model that checks a marker file in the home folder could never see it and repeated its first-run question in every `auto`/`yolo` session.
- **Session advisor.** `/advisor <model-key>` (or `on` for the strong tier) sets an advisor for the session: from the next turn the main model gets a read-only `advisor` tool (a `question` and optional `context`) and a short system-prompt note to consult it before a large or risky plan, when stuck and before finishing a risky change, sparingly. The tool sends the condensed conversation, the turn in flight included, and the question to the advisor model and returns the answer as its result; a failed consult comes back as a tool error and the main model carries on. A bare `/advisor` shows the advisor, `/advisor off` clears it, and `--default` also writes `autonomy.advisor` to the user config. `/advisor ask [question]` is the old one-shot critique (free text of two or more words still works that way) and `/advisor accept` adds the last critique to the conversation. A single word that is no model key (`/advisor foo`) is refused as an unknown model key instead of sent as a question. `/settings` reports the advisor.
- **Settings panel.** In the TUI `/settings` opens an interactive settings panel instead of printing text. The Config tab edits the model, reasoning effort, permission mode, output style, theme, show thinking, tool details, compact layout, status bar, busy indicator, Enter-while-busy and mouse: `↑`/`↓` or `j`/`k` move, `←`/`→` or `h`/`l` change a value, `Enter`/`Space` cycle or toggle it, `/` searches, `1`-`9` jump, `PgUp`/`PgDn`/`Home`/`End` scroll, `Tab` switches to the read-only Status tab, `Esc` or `q` closes. Each change runs the existing slash command (`/model x`, `/permissions mode plan`, ...), so it applies live and persists as that command does. Keys are ignored while an approval or question prompt is open. `/settings status` (or `text`) keeps the paged text view. New RPC `settings.get` returns the structured view, which now also lists `model_keys` and `permission_modes`.

### Fixed
- **Hardline: a command in backticks nested in backticks is checked (K3NOX-586).** Inside backticks bash ends the payload at the first backtick that is not escaped and drops the backslash of `` \` ``, `\\` and `\$` (in double quotes also of `\"`) before it runs it. The parser ended the payload at the escaped backtick and never unescaped it, so with `` echo `echo \`rm -rf ~\`` `` (also in an assignment, double quotes, `bash -c`, `$(...)` or an unquoted heredoc body) nothing reached the `rm` check and `yolo` ran it. The payload now ends and is unescaped the way bash does it, on the command line and in heredoc bodies, so these are denied in every mode, and backticks nested more than six levels deep count as nesting and are denied (`scan-depth`). The argument of a double-quoted `bash -c`, `sh -c` or `eval` is unquoted the way the shell does it too (`` bash -c "echo \`rm -rf ~\`" `` was allowed in `yolo`), with a `$(...)`, backtick or `${...}` in it read as one unit whose quotes are its own, and a heredoc-body backtick with `\"`, which bash and dash read differently, is checked both ways and no rule vouches for it. An escaped backtick bash prints as text (`` $(echo \`x\`) ``, inside single quotes, `` \\\` ``) stays text.
- **Hardline: the new payload readings only add to the old ones (K3NOX-622).** The unescaped backtick payload, the unescaped heredoc-body payloads and the quote-aware launcher words (K3NOX-586) replaced what the parser read before, so a few commands it flagged could slip through. It now reads both: the text up to the next backtick (and the scan resumes there, as before), the raw body payload and shlex's words are checked next to the new readings, and a test pins commands denied before as still denied. Readings of one unit are not read twice over at every level of nesting: an identical reading is parsed once, the characters of every reading after the first are charged to the scan budget, and a command past it is denied (`scan-budget`) in every mode (a 100 KB command nesting heredoc-body backticks 6 deep took 210 s in `decide()`, it now takes under 0.1 s).
- **An event sink that fails no longer aborts a failover (issue #148).** The router called its event callback unguarded, so an error in a listener (the gateway's status update to a client that had gone) raised out of the failover walk and failed the turn instead of the next provider being tried. The error is now logged and the walk goes on.
- **Hardline: escapes inside `${...}` in a double-quoted `bash -c` argument are read as the shell reads them (K3NOX-615).** In `"${x:+...}"` bash and dash drop the backslash of `` \` ``, `\$`, `\"`, `\\` and `\}` before the inner shell sees the text, but the parser kept the `${...}` as written, so `` bash -c "${x:+\`rm -rf ~\`}" `` (also nested `${y:-...}`, `sh -c`, `eval`) reached no check and `yolo` and `auto` ran it. The `${...}` in a double-quoted launcher argument now loses the same backslashes, so these are denied in every mode; `` \\\` `` there stays text, and a `$(...)` or backtick in it is read as before.
- **Hardline: a command nested deeper than the parser follows is denied (K3NOX-551).** The shell parser the hardline reads stops after six levels of nested commands (`$(...)`, `<(...)`, backticks, `bash -c`, `eval`, a heredoc a shell runs), but only its scan budget turned stopping short into a deny: past that depth the commands in there were never checked, and `auto` and `yolo` could run them. A command nested more than six levels deep is now a hardline deny in every mode (`scan-depth`, next to `scan-budget`). A command the parser gives up on is also decided quickly: once the deny is certain the per-command checks are skipped, so 50,000 nested `$(` take well under a second instead of 49 s. Commands nested six levels or less decide exactly as before.
- **`k3code export` no longer hangs or crashes on a hostile project config, and reads nothing outside the project (K3NOX-585).** A cloned repo's `.k3code/config.yaml` with a YAML alias bomb, thousands of nested brackets, a huge size or a FIFO made the export (and `/export` in the gateway) spin, run out of memory, die with a `RecursionError` or block for good, and a symlink out of the project had its target exported. The project config is now read as a regular file of at most 1 MiB, without aliases and at most 64 levels deep, and a symlink must stay inside the project; otherwise the export stops with the one-line `does not parse` error. Trust checks skip a FIFO or oversized config the same way. The file's place is read off the opened file (`/proc/self/fd` on Linux, `F_GETPATH` on macOS, which has no `/proc`), so a link swapped while it is opened is refused too.
- **Auto fan-out has a budget (issue #136).** A `large` or `huge` plan fanned out in `auto` mode ran with no agent or token cap: up to 8 subtasks, each with a worker, a reviewer, a rework and a re-review, every child allowed 200 model calls. Only `/ultracode` passed a budget. The auto fan-out now stops starting children at `autonomy.fanout.max_tokens` (default 1,000,000; 0 = no cap) or `autonomy.fanout.max_agents` (default 0 = 4 per subtask, at most 16; a worker only starts while a reviewer slot is left), and every fan-out, `/ultracode`'s included, also stops once the session's `reliability` session or day budget is spent. The subtasks left are reported as `skipped` with the reason (`Stopped early: agent budget exhausted (16/16 agents)`) and the main model finishes them.
- **`k3code -p`, the line REPL and sub-agents apply your configured permissions.** They built their permission state without reading the config, so your `permissions:` rules and the extra patterns under `permissions.hardline` (user config, trusted project config, accepted project rules) were never applied there, in any mode; only the gateway's own session turns read them. Every permission state now reads them before its first decision. `-p` and the REPL take the project's rules from `--config-dir` when it is given, and a worktree sub-agent takes them from its parent's project. A project config you have not trusted still contributes nothing, and the built-in hardline list is unchanged. Allow and ask rules from the config now apply in `-p` and the REPL too, so a command an `allow` rule covers runs there without asking.
- **`k3code -p TEXT` no longer hangs on an idle stdin above descriptor 1023.** The wait for piped stdin polled with `select()`, which raises on a descriptor number of 1024 or more; that was treated as "ready" and ended in a blocking read of the idle pipe. It now polls with `selectors` (epoll), and a stream it cannot poll (in memory, or a redirected file) is still read straight away. The core test suite also closes the SQLite stores that its gateway tests left open (about 17 descriptors per test), which is what pushed a later test's pipe above 1023 and hung `pytest` at `test_an_idle_open_pipe_does_not_hang_the_run`. (K3NOX-563)
- **A blank `permissions.hardline` entry no longer denies every command.** `hardline: ['']` matched any text, so plain `ls` and `curl` were hardline denies. Blank or whitespace-only patterns are now ignored; the config load log and `k3code doctor` name each one, and the setup wizard no longer writes an empty answer as an entry.
- **Auto mode no longer prompts for reads outside the project.** An out-of-project `read`/`grep`/`glob` in auto mode is allowed under read-only system and toolchain locations (`/usr`, `/opt`, `/etc`, `/nix/store`, `~/.cargo/registry`, `~/.rustup`, `~/go/pkg/mod`, `~/.npm`, uv pythons, `site-packages`/`node_modules`) and otherwise refused with a hint to stay in the project or `/add-dir` it. Credential paths stay hard-denied, user/project read rules still win, and default mode still asks.
- **Auto mode started in `$HOME` no longer asks before every command.** A plain, non-recursive `ls`, `cat` or `grep` the builtin read-only allowlist allows runs in a sandbox that shows `$HOME` read-only, without network, with credential folders and files, shell histories, agent and cloud logins, browser profiles and top-level dotenv files hidden (symlinked ones at their target); anything else still asks a person: recursive searches (`grep -r`, `rg`, `ls -R`), globs, `git`, and commands only your own allow rules cover (`python3 *` would read all of `$HOME`). The session is told once that it started in the home directory.
- **`k3code export` hides a config's secrets even when the config does not load (K3NOX-519).** With one setting that failed validation, the export knew only the secret-named environment variables, so a copy of an MCP `env`/`headers` value or of a `*_env` reference elsewhere in the settings or in a session could leave in clear. The known values now also come from the user config and the trusted project config as written, and every exported file hides its own values (an untrusted project config's values hide nothing outside that file).
- **`k3code export` hides an untrusted project config's values in sessions, and a config that does not parse is refused without its text (K3NOX-575).** A project config that was never trusted, or changed after it was trusted, named no secrets for the export, so an exported session that quoted one of its MCP `env`/`headers` values kept it in clear. The export now reads the project config as written whatever its trust state and hides its values in the sessions (not the guessed ones, such as a region or path). It still loads no setting from that file and hides nothing in your user settings file. A trusted, unchanged project exports exactly as before. A project config that does not parse now refuses the export whether it is trusted or not, `--session-only` included, with the one-line `… does not parse` error. Before, `--session-only` went ahead, and a full export failed with the parser's own error, which quotes the offending line in a traceback or in the `/export` reply. The refusal for any config file no longer carries the parser's error as its cause either.
- **`k3code export` and `/debug dump` hide a project's `.mcp.json` values (K3NOX-581).** Neither read `.mcp.json`, so a session or event that quoted one of its MCP `env`/`headers` values, such as an API token, kept it in clear in the bundle unless the shape scrubber happened to catch it. Both now read the `.mcp.json` of the project you export from and of each exported session's (or dumped event's) project as written, trusted or not, and hide its values in the sessions and events. They hide only the values that a secret name or a credential shape marks, not guessed ones such as a database name. Your settings files are exported as before. A value known only from such a file (this `.mcp.json`, or a project config you have not trusted) is now hidden after the credential-shape scrubber has run, not before it, together with any part of it the scrubber or a known value left beside its own `<redacted>`; a text where that search would take too long (many long such values beside many markers) is hidden whole instead. Hidden first, a value that is an ordinary word around a credential (a header keyword, a parameter name) could keep the scrubber from recognising the credential next to it, which then stayed in clear. **Behaviour change:** a `.mcp.json` that does not parse (invalid JSON, not UTF-8, nested too deeply) now refuses an export that includes sessions, and `/debug dump`, with the one-line `… does not parse` error, which names only the path. A `--settings-only` export does not read it.
- **Hardline: a comment right after a substitution open, and a quadratic arithmetic scan.** Two gaps in the shell parser the hardline reads. A `#` directly after a command-substitution opener (`$(`, `<(`, `>(`) was kept as literal text instead of starting a comment that bash and dash both run to the end of the line; a command line could use that to make the parser close the substitution early, read the next line as a heredoc body and so skip a command the shell actually runs (auto and yolo allowed it). The `#` now starts a comment there, as in the shells, so the hardline sees the command. Separately, the scan that finds the end of an arithmetic command (`((...))`) ran at every `(` and read to the end of the text each time, so a long run of `(` was quadratic on the loop that decides a command (a few thousand took tens of seconds). One budget now caps the characters that parsing a whole command may scan for parens — shared across its substitutions, quoted strings and nested `$(...)`, so none of them can multiply it. A command that nests substitutions too deeply is left unterminated so a person confirms it; one that runs past the budget is a hardline deny (`scan-budget`, in every mode: auto, yolo and default), because the parser can no longer tell where a substitution ends and the commands after it would go unchecked. The budget counts scanned characters, so nesting multiplies it: 25k characters nested three levels is about 122k of budget and is denied.
- **A malformed permission rule no longer disables the rest of its file.** One entry in a `permissions:` section whose action was not exactly `allow`, `ask` or `deny`, or a tool value that was not a mapping, made k3code drop every rule of that file, deny rules included, without a message; `auto` then ran what those rules denied. This applied to your `config.yaml`, a trusted project config and the rules accepted from a project recipe. Such an entry is now enforced as a deny (for its pattern, or for the whole tool when the pattern or the tool value cannot be read) and the other rules stay; a file whose `permissions:` cannot be read at all denies every call no other rule allows. Each problem is logged once, naming the file and the entry (never the pattern), and `k3code doctor` lists them in a new `permissions` check.
- **A malformed `permissions.hardline` fails closed instead of crashing.** A `hardline` value that was an int or `true` stopped `k3code doctor` with a `TypeError` traceback and aborted every gateway turn. A string was split into one regex per character, so `^` refused every shell command without a word. An item that was not text, or not a valid regex, was used anyway (the bad regex then failed every shell command). A retry that cannot be read as shell is never learned. A failure with no such retry still waits for the third sighting and a card you accept.

- **The skills curator archives a skill by its directory, and only inside the skills dir (issue #162).** A proposal to archive a stale or duplicate skill moved `skills/<frontmatter name>`, so a skill whose `name:` differs from its directory was reported "not found", and a `name:` such as `../outside` moved a directory next to the skills dir into `_archive`. The proposal now carries the directory name (`dir`), and accepting it refuses anything that is not a skill directory directly under the skills dir (`..`, a path, an absolute path, `_archive`). Proposals queued before this change still work by their old name.

- **`/memory mem0 <query>` finds what k3code stored (issue #162).** The search named no `agent_id` (and a `user_id` only when `mem0.user_id` was set), so with the default config upstream mem0 refused it for naming no owner, and with a `user_id` it did not look for the `agent_id` the writes carry. The search now sends the same `agent_id` and, when set, `user_id` as the writes of `store_mem0` (one `Mem0Config.identifiers()` for both). mem0 is still read only by this command; k3code does not recall from it on its own.

- **Skill cards from a session review can be read, are not repeated, and clean up after themselves (issue #161, finding 9).** "Save skill 'x'?" asked you to accept a SKILL.md you could not see. The card now starts the body, and `/proposals show <id>` prints the whole SKILL.md that accepting saves. A skill whose body is like a live skill or like any earlier skill card (dismissed ones included) is no longer a new card, so a reworded name does not come back at every review, and a later review can no longer rewrite the draft under a pending card. Skill cards go through the same ranker as other proposals (a project that keeps dismissing them stops getting them) and a project gets at most `learning.skill_cards_per_week` (default 3) new ones a week. Dismissing a skill card deletes its draft, and the daily curator pass deletes drafts in `skills/_drafts` that no pending card waits on (older than a week). The description on the card is scrubbed of secrets like the draft's.

- **Learned notes are reconciled and expire (issue #162).** The session review never saw the notes it had already written and added each new wording after the last (exact duplicates only, oldest dropped at 30), so reworded duplicates, contradictions and stale facts piled up in `learned.md`. The reviewer now gets the existing notes, numbered, and may `update` a note, `delete` one that is wrong, obsolete or repeated, and `keep` one the session confirms (at most 5 of each per review); a new fact that differs from a note only in case or punctuation confirms that note. Each note the review writes ends in `<!-- seen YYYY-MM-DD -->`; a note no review has confirmed for 90 days leaves the prompt and is dropped by the next review, and at 30 notes the longest-unseen goes first. A line you write yourself has no stamp and never expires. Facts mirrored to mem0 are the new and reworded ones only; a note deleted here is not deleted from mem0.

- **A mem0 outage no longer costs a worker thread 10 s per item, and review facts mem0 did not take are posted later (issue #162).** The writer that sends learned preferences and review facts to mem0 tried every item even when mem0 did not answer (12 items against a blackhole kept a worker thread busy for about 120 s). It now stops at the first post that fails to connect, times out or is refused for a reason other than one bad body (401/403, 429, 5xx), and connects within 2 s. Everything not yet sent waits in `$K3CODE_HOME/learning/mem0_outbox.json` (0600, newest 200 kept) and goes out first on the next pass, a review's or the daily distill's; a review fact is derived once, so a failed post used to lose it. A body mem0 refuses (400, 413, 422) is dropped and does not stop the pass.

- **A secret written as a sentence no longer reaches a memory fact or the review model (issue #162).** The scrubber only masked `NAME=value` shapes, so "the DB password is hunter2hunter2" and "deploy token is <32 hex digits>" passed through `clean_fact` into `learned.md` and were mirrored to mem0, and the session transcript went to the cheap-tier review model unscrubbed. `scrub_text` now also masks a credential word (`password`, `token`, `secret`, `api key`, `key`, ...) followed by `is`/`was`/`set to` and a value that is quoted or has a digit, wherever it is used (session exports, debug dumps, decision logs). Memory facts and the review transcript are additionally scrubbed of any bare run of 32+ letters and digits that has both; a fact that names a full 40-character commit hash is therefore dropped (short hashes are fine). Tests: `core/tests/test_redact.py`, `core/tests/test_learned_notes.py`.

- **Building the prompt no longer runs `git config` every time (issue #166).** `gotchas_prompt` looked up the project's id with a blocking `git config --get remote.origin.url` (3 s timeout) on every prompt build, which is every turn and every token estimate. The id is now kept per directory and looked up again only when the repository's `config` file changes (a worktree reads the main repository's), so a remote added or changed mid-session is still seen on the next build.
- **Config errors no longer show part of a provider key (issue #167).** A provider block in `config.yaml` that failed validation (no `base_url`, `name` or `kind`) made the error repeat the whole block, including the end of the API key from `api_key_env` or the env file. The key is now filled in only after the config has been validated, and it no longer appears when a loaded config is printed. The error still says which provider block is wrong and why.

- **The fan-out reviewer gate fails closed (issue #97).** A reviewer that failed, was stopped, ran out of budget or answered without a `VERDICT:` line counted as a pass, so unreviewed work was merged. The gate now opens only on a reply that ends with `VERDICT: pass`; a pass line earlier in the reply, a quoted one, `VERDICT: passing` or the stop message of a reviewer whose commands kept failing is no verdict. A reviewer without a verdict is asked once more, and then the subtask is escalated to the parent with its branch kept (the worker is not sent back, since its work was never judged). Work a worker redid after a merge conflict or failed tests is reviewed again before it is merged. The reviewer is told which worktree and branch hold the change, and when the diff in its prompt is cut at 20,000 characters it is told so and reads the rest there. In `/ultracode`, a review lens that fails or replies without the findings array is asked once more and the report then says `review INCOMPLETE` instead of "review panel found nothing", also when the agent budget stops the panel; a cut diff is noted the same way.

- **Edit and write approvals show the change (issue #131).** The approval prompt for `edit` and `write` showed only `edit <path>`, so you approved file changes without seeing them. The request now carries a unified diff (`preview`): for `edit` it comes from the edit tool's own matching, so a whitespace-tolerant match shows the line that will really change; for `write` it diffs against the existing file or lists a new one. It is capped at 200 lines (400 characters each), files over 2 MB are not read, and an edit that will fail says so. The TUI shows it under the command with added and removed lines coloured, 16 rows at a time; `[` and `]` page through the rest. Clients that do not know the field ignore it.

- **TUI: Esc closes `/settings`, Enter returns to the bottom, start keeps your scrollback.** Esc now closes the `/settings` panel (it clears a search first) as its footer says; only `q` worked, because Ink flags every Esc as an Alt key and the panel ignored those. Sending a prompt or a slash command scrolls the transcript to the bottom, so the echo and the reply are visible after you scrolled up. Starting the TUI no longer writes `ESC[3J` (twice: before entering the alternate screen and with it), which erased the whole terminal scrollback of the shell it was started from; only the visible screen is cleared (#151, #154, #155).

- **The TUI uses a Node that is new enough (#94).** `k3code` took any `node` on PATH, so a host with Ubuntu's Node 18 first on PATH crashed the TUI at start ("Cannot use import statement outside a module") although the installer had fetched a private Node 22. The node is now `K3CODE_NODE` if set, else the installer's private Node under `<data>/node`, else a `node` on PATH only if it is Node 20 or newer (versions compared as numbers). With none, k3code says which problem it found (for example "Node >= 20 required (found v18.19.1 ...)") and how to fix it, and `k3code doctor` names the node it uses and why.

- **`/memory add --user` lines survive the daily distill.** The distiller rewrote everything from `## Learned preferences (auto)` to the next heading, and `/memory add --user` appends at the end of `USER.md`, so after the first distill every added line was erased within a day (issue #91). The managed block now ends with `<!-- /k3code:auto -->` and only the lines from the heading to that marker are rewritten; everything else in `USER.md` is left byte for byte. A `USER.md` from before the marker is migrated on the next distill without losing a line: lines the previous distill wrote (`learning/preferences.json`) go, anything else in the old section stays and moves above the heading.

- **Re-running a setup step keeps your data (#92, #93).** `k3code setup` and `setup --step about|system|usage` no longer overwrite `USER.md`: the answers live in a block between `<!-- k3code:setup begin ... -->` and `<!-- k3code:setup end -->`, and your own lines and the learned preferences around it are left alone. A `USER.md` from an older setup is copied to `USER.md.bak-<time>` once and gets the block. A step now writes only the config keys it owns, each inside its section (for example `display.theme`, not all of `display`), so display settings, other `autonomy` keys and permission rules survive a re-run. `setup --step tiers` takes the provider chain from `config.yaml` instead of the saved setup answers, so it no longer empties or reverts the chain after a fast onboarding, and it changes only the tier models of those entries (an entry left blank keeps the models it has); `setup --step providers` keeps the other keys of an entry it already has and says that it replaces the chain. `setup --step summary` on its own leaves `config.yaml` alone: only the summary at the end of a full run writes it.

- **`k3code update` keeps the last good version (#95, #158).** An update whose TUI did not build (the npm registry unreachable) used to switch to a version without the TUI and report "updated" with exit 0: the installer now fails that build when `k3code update` runs it, and the update compares the new version with the active one and refuses to lose the TUI, keeping the active version and pruning nothing. A k3 binary that did not build (Go modules unreachable) is reported after the switch ("warning: ... has no k3 multi-window binary"), and `prune` keeps the newest version that still has it. `prune` now keeps the newest builds by build time (it ordered `-src.<sha>` versions by the sha string, so it kept an old build and deleted a newer one) and never removes a version directory that a running daemon, TUI or gateway executes from (read from `/proc`), which broke their lazy imports (`/doctor failed: cannot import name 'probe'`).

- **Heredocs in the permission checks.** The shell expands the body of a heredoc with an unquoted delimiter (`cat <<EOF`), so a `$(...)` or backtick in it runs. Such a command no longer matches the read-only allowlist (it asks), the payloads go through the hardline checks like any other substitution, and the script a heredoc feeds to a shell (`bash <<'EOF'`, `cat <<'EOF' | sh`) is checked like `bash -c`. A heredoc an interpreter runs as its program is never covered by an allow rule, and one fed to `ssh host` with no remote command is a script for that host, checked command by command like `ssh host '...'`. The delimiter and the end of the body are found the way bash finds them (the whole word with its quotes removed, a quote anywhere in it makes the body data, a delimiter line that matches exactly, `\<newline>` joined in an unquoted body, a `<<` in `((...))` is a shift, also when the `))` is on a later line); a `<<` the parser cannot place needs a person and the lines after it are checked as commands, so the hardline sees them in `yolo` too: one inside a `${...}`, `$[...]`, subscript or `a=(...)` that is still open, however far back on the command it opened, after an `a=(...)` that bash rejects, after a `$(...)` that ends inside such a bracket, a word bash versions read differently, a heredoc opened in a `$(...)` that ends on its line. A quoted delimiter still keeps the body as data.
- **Protected files for `write` and `edit`.** Editing a file that git, direnv, husky or a shell runs as code, or that holds credentials, now always asks, in every mode including `auto` and `yolo`, and no allow rule turns that back into an allow (a deny rule still denies): `.git` at any depth (its config, hooks and `info/`, and the `.git` file of a linked worktree), `.gitattributes`, `.gitmodules`, `.envrc`, `.husky`, `.k3code/config*`, and in the home directory the shell startup files, the git config, `~/.ssh` and the other credential directories. The match ignores case and follows symlinks, also when a `..` comes after a link (`link/../config`), and `read`, `grep`, `write` and `edit` judge the project roots and the credential files by the file a `link/..` really reaches. Headless, background and sub-agent runs are refused instead of asked. The harness's own git (scope classification, worktrees, git triggers) no longer reads the system or global git config, and its diffs skip external diff and textconv programs; `HARNESS_GIT_CONFIG` in `reliability/sandbox.py` says what that cannot prevent.

- **The crash-resume transcript is appended to, not rewritten (issue #72).** After every step and tool result the loop serialised the whole conversation and rewrote `journal/<session>.messages.json` on the event loop, so a long turn with large tool results wrote gigabytes and stalled the loop for tens of milliseconds per step (one session's file reached 376 MB). The file is now JSON Lines: a save appends only the new messages, and the file is rewritten only when it no longer matches the conversation (a resume, another loop on the session, a file removed underneath). A transcript in the old format still resumes, and a last line cut off by a crash is skipped.

- **Fan-out and uncommitted changes (issue #98).** Fan-out merges every subtask into your checkout, and git refuses that merge while a staged edit (or an edit to a file the subtask touches) is in the way. Each refusal was reported as a "merge conflict", cost a rework agent that could not fix it, and then escalated. Fan-out now starts only on a checkout without uncommitted changes to tracked files; otherwise it says so (`fan-out skipped: the checkout has uncommitted changes (...)`) and the turn runs as one agent. A merge git refuses later (you edited the checkout while the workers ran) escalates at once with "the merge did not start: uncommitted changes in the checkout are in the way (not a conflict)" and git's list of files; the work stays on its `k3/<id>` branch.

- **Sandboxed commands resolve host names when `/etc/resolv.conf` is a link (issue #137).** The bash sandbox showed only `/usr`, `/etc`, `/run/systemd/resolve` and `/run/NetworkManager`, so where `/etc/resolv.conf` links elsewhere (WSL 2: `/mnt/wsl/resolv.conf`; Debian resolvconf; `/var/run/...`) every command in auto, yolo and unattended runs had a network but no name resolution, and `git fetch`, `pip`/`npm install` and `curl` failed. The name-lookup files (`resolv.conf`, `hosts`, `nsswitch.conf`, `host.conf`, `gai.conf`) are now followed link by link and the file they end at is shown read-only at its own path, never one under `$HOME` or the k3code home. `k3code doctor` reads them inside a real sandbox and warns when one is missing there; it used to report OK.

- **`web_fetch` keeps code, links and tables (issue #99).** The built-in `web_fetch` and `web_browse` collapsed whitespace over the whole page, `<pre>` included, so code samples lost their indentation; links lost their targets; and table cells ran together (`timeoutint30`). Pages now arrive as Markdown: `<pre>` blocks verbatim in a ```` ``` ```` fence, links as `[text](url)` resolved against the page's URL after redirects (in-page `#` anchors, `javascript:` and `mailto:` links stay plain text, a link without text is left out), and table rows as `| a | b |` (a row that holds code or runs past 1,000 characters is page layout and keeps its line breaks). Entities are decoded once, so a link with `&section=` in its query no longer turns into `§ion=`. A page fetched over HTTP is now parsed off the daemon's event loop, as a page read in the browser already was.

- **`write` no longer replaces changes it has not seen (issue #100).** `write` and `edit` refuse an existing file the session has not read, or one that changed on disk since the session last read, wrote or edited it (your editor, a formatter, another agent), with "read it before you write it" or "changed since you read it ...: read it again". Before, `write` replaced the whole file and an edit you had saved in the meantime was gone without a word. A new file needs no read, and what the session wrote or edited itself it may change again. A session remembers this across its turns and tiers; a sub-agent and the plan-first executor read for themselves.

- **One browser per site, and none kept forever (issue #102).** Several `web_browse` or escalated `web_fetch` calls in one reply that hit the same site started a Chromium each on the same profile (and a second Playwright driver); they now share one launch. At most 3 sites keep their Chromium open (the least recently used closes first, never one that is still being read), and a site unused for 5 minutes closes; the next read relaunches it. Browsing many hosts used to leave a Chromium (150-300 MB each) per host running until the gateway stopped.

- **`k3code doctor` finds the Chromium the installer puts in (issue #104).** Playwright 1.63 names the headless shell `chrome-headless-shell`, and the browser check only looked for `chrome` and `headless_shell`, so every fresh install (and the installer's health subset) warned "no executable browser; the browser tool is off". When the directory really holds no browser, the fix now names the `playwright install --force --only-shell chromium` command; re-running the installer did nothing, because it skips a Chromium directory that is already there.

- **The daemon token gates every method that acts (issue #167).** Only a short list of methods needed the `gateway.auth` token, so a connection without it could still start or steer a turn, undo, attach to or create a session, or attach files. Now a connection without the token may only call reads of k3code's own state (`setup.status`, `session.list`, the settings view and the like), and a new method needs the token until it is listed as such a read. The bundled clients (the TUI's attach bridge, `k3code slash`, `k3code doctor`) are unchanged. A script that talks JSON-RPC to the socket itself must send `gateway.auth` first, as they do. The `gateway/auth.py` docstring now says what the token guards against (a peer that can reach the socket but not the run directory) and what it does not (an unsandboxed process of the same user, such as an MCP stdio server, can read the token).

- **Setup offers current chat models first (issues #121, #122).** The model lists in `k3code onboard` and in the tiers step of `k3code setup` were the endpoint's ids in alphabetical order, so an unattended `k3code onboard --answers` without `onboard.model` made the first id the default model (`babbage-002` on OpenAI), and an OpenRouter menu began with `01-ai/yi-large`. Embedding, speech, image, moderation and legacy completion ids are now left out; Claude, GPT and Gemini models come first, newest first, then the rest. An answers file without a model gets the top one. Each menu shows at most 15 models, with `(type one)` at the top and the top model preselected.

- **A provider that answers is not "offline" (issue #124).** The connectivity monitor called the host OFFLINE whenever its generic probe (gstatic `generate_204`, then TCP 1.1.1.1:443) failed, whatever the providers did. With only a local or LAN provider (Ollama, vLLM, an OmniRoute on the tailnet) on a host with no internet, or with those two hosts blocked, one transient connect error paused the turn until `/stop` and the status line said "offline" while the provider was fine. A provider endpoint that answered its own probe in the latest round now keeps the state ONLINE, so the turn parks and retries on the normal ladder; with no provider answering the state is OFFLINE as before.

- **An approximate `edit` says what it replaced (issue #103).** When `old_string` is not in the file and `edit` falls back to a similarity match (`block_anchor`, `context_aware`), it may rewrite a similar but different text: `TIMEOUT = 30` for an `old_string` of `TIMEOUT = 35`. The result said only `Edited: 1 replacement (matched by context_aware, not exactly)`; it now also gives the line numbers and the file's text that was replaced, so the model sees what it changed.

- **`grep` globs.** An `include` or `exclude` glob with a slash (`tests/*.py`, `src/**`) now means the same with and without `rg`: it is anchored at the searched directory, as `rg -g` does, and `**/` matches at any depth. Before, the Python fallback compared only the file name and found nothing, and `rg` anchored the glob at the daemon's working directory instead of the project. A pattern that neither `rg` nor Python accepts (`foo(`) now fails with `rg`'s message instead of Python's (#139).

- **Auto mode without a sandbox asks first (issue #135).** Where bubblewrap is unusable (macOS, WSL or Linux without it, user namespaces disabled), an interactive `auto` session ran every command it allowed directly on the host (`rm -rf ~/Documents`, `git push -f`, `powershell.exe` from WSL), with nothing in the session but a log line. It now asks before each command that only the sandbox made safe; allow rules and the read-only allowlist still run without asking, as in `accept-edits`. `yolo` still runs everything. In both modes, from the first command on, the session shows a sticky warning until it leaves `auto`/`yolo`. `k3code -p --permission auto` and the REPL cannot ask, so they refuse those commands and say why on stderr.

- **A prompt survives a dropped terminal (issue #152).** The prompt reached `sessions.db` only with the model's first tool call or at the turn's end, so closing the terminal (SIGHUP, an SSH drop) or a kill while the model was still answering left a session with no messages that `/resume` did not list, and the prompt had to be typed again. It is now saved as the turn starts, before the first model call; a prompt drained right after the previous turn is saved too.

- **Worktrees and branches of dead fan-out and sub-agent workers are reaped (issue #159).** A worker's checkout `.k3code/worktrees/<id>` and its branch `k3/<id>` were removed only when the process that made them got to clean up, so a daemon crash, a kill, a reboot or a worker that failed left them for good. When a gateway starts it now goes through the repositories its newest sessions worked in: a worker checkout whose process is gone is committed to its branch and removed (a checkout whose process still runs, or one that `/branch --worktree` made, is left alone), `git worktree prune` runs, a `k3/*` branch already merged into `HEAD` is deleted, and one with unmerged work is kept for 30 days after its last commit, then deleted with its tip written to the log (`git branch <name> <sha>` brings it back). `k3code doctor` and `/doctor` list what is left in the current repository under `worktrees`. A merge a dead fan-out left half-done is not detected yet.

- **`claude` on PATH is not a Claude Code login (issue #146).** Fast setup offered `claude-cli` as "found" and `k3code doctor` showed it green on the `claude` command alone, so the first turn then failed with "The model provider rejected the API key" and a `k3code onboard` hint that does not apply to a provider with no key. Both now run `claude auth status` (about a second): setup leaves a logged-out `claude-cli` out of the providers it found and says to run `claude`, then `/login`, if you pick it anyway (also in the unattended default); doctor warns the same; and a failed turn whose error is Claude Code's "Not logged in / run /login" now reads "Claude Code is not logged in. Run `claude` and /login, then /retry." A Claude Code that cannot answer (an older one, a timeout) raises no complaint, and `--no-probe` skips the check.

- **Fast setup no longer keeps a key the endpoint rejects (issue #147).** `k3code onboard` (fast) now checks the key against the endpoint's model list before it stores it, also when the answers file names a model. An HTTP 401/403 stores nothing and writes no config: with `--answers` it exits 1 ("K3CODE_API_KEY was rejected by ..."; `--no-probe` skips the check), interactively it asks for the key again, up to three keys (showing the length and last four characters of the one tried), and then offers to save anyway or give up. A key that was never given is not a rejected one, so provisioning that injects it later still works. Quotes, `export`, `NAME=` and `Bearer` around a pasted key are removed. A failed check says what to look at: the key, a URL with no models list (404), a redirect (with where it leads; it is not followed), or an endpoint that cannot be reached (interactively: retry, save anyway or cancel). A rejected key no longer overwrites a working one in the env file.

- **The total memory cap keeps the nearest files (issue #144).** With more than 40,000 characters of memory, the prompt dropped the files nearest the working directory first (a large root `CLAUDE.md`, `AGENTS.md` and `K3CODE.md` left no room for `pkg/K3CODE.md` in `pkg/`). The budget now goes to your `USER.md`, then to the instruction files from the working directory outward, then to `.k3code/rules`; what does not fit is the root's tail or whole root files, and the files that fit stay in their order, nearest last.

- **`k3code update` from a drive root (issue #157).** The update's smoke test ran `doctor` in the directory the update was started from, and the project scan died on an entry a Windows drive root denies `stat` on (`PermissionError: ... /mnt/c/pagefile.sys`), so `cd C:/ && k3code update` refused a healthy new version. The smoke test now runs inside the new version, its failure message keeps the last 400 characters of stderr (the cause comes last in a traceback; it kept the first 200), and the stack scan behind `k3code doctor`, `setup` and project preparation skips an entry it cannot stat instead of crashing.

- **A recorded tool failure no longer reads the whole 14-day window of tool errors (issue #161).** To decide whether a failure is a recurring pitfall, every failed tool call loaded and JSON-decoded all `tool_error` rows of the last 14 days of its project on the daemon's event loop: about 6 ms at 1,000 rows, 66 ms at 10,000 and 300 ms at 40,000. The lookup now asks SQLite for just that signature and tool through a new `decisions` index (`kind, project, subject, ts`, created when the database is opened), about 0.03 ms at any size. Which failures become gotchas is unchanged.

- **A failed `/proposals accept` leaves the card pending (issue #161).** The command marked the card accepted and logged the decision before the handler ran, so a handler that raised (a skill draft that was gone, say) latched the card as accepted: the error was shown, but the card could not be accepted again and the store would never propose it a second time. The handler runs first now; the card is marked accepted and the decision logged only after it succeeded, and after a failure the card stays pending for another try.

- **A gotcha is learned only from a real retry (issue #161).** The learning hub paired a failed tool call with the next successful call of the same tool whenever the two shared one word (`npm test`, then `cat package.json | grep test`), or with any successful `read` or `edit` whose arguments differed, and with a call the model asked for in the same reply, before it had seen the failure. Such pairs became a "worked instead" hint, which two sightings turned into an auto-noted line and a card. Now the retry must be the next call of that tool in a later model reply, and a `bash` retry must be the failed command with other options or operands (same program and first operand, so `git push` and `git push --set-upstream origin main`) or the only command and the same operands under another program (`python x.py` and `python3 x.py`). Other tools get no hint (`worked with different path` said nothing), so a failing `read` waits for the card at three sightings.

- **Setup gives each custom endpoint its own key variable (issues #114, #120).** Every custom endpoint used to read its key from one shared `K3CODE_API_KEY`: fast setup reused a key left there for another vendor without asking and sent it to the new host, and a second endpoint (fast setup run twice, or two custom entries in the wizard) overwrote the first one's key, while fast setup also dropped the first entry. Each custom entry now gets its own variable, `K3CODE_<NAME>_API_KEY` (`K3CODE_ENDPOINT_API_KEY` for fast setup, `K3CODE_ENDPOINT_2_API_KEY` for a second endpoint), and fast setup keeps an endpoint with another URL as a fallback. Re-running fast setup for the same endpoint keeps its variable, including an old `K3CODE_API_KEY` that no other endpoint uses. When the variable already holds a key, fast setup asks whether to keep it, says whether it is in your environment or in the env file, and takes a replacement. If you decline it and give no new key, the declined key is not used for that endpoint: a custom endpoint moves to a new, unset variable (`k3code onboard` says so), a vendor preset keeps its fixed variable and the old key stays stored, and no model listing is tried with it. The full wizard follows the same rules: a new entry never gets a variable that already holds a key (a re-run for the same URL keeps its own), and a vendor preset's variable (`OPENAI_API_KEY`, ...) is used only at that vendor's own URL, so an `openai` entry for another host gets its own variable. For the old shared `K3CODE_API_KEY`, the keep question now defaults to no and says the key may belong to another endpoint.

- **`k3code doctor` no longer crashes from a Windows drive root (issue #111).** The stack scan checked every entry of the working directory with `Path.is_dir()`, which before Python 3.14 raises `PermissionError` for an entry the filesystem refuses to stat (`swapfile.sys`, `pagefile.sys` and `hiberfil.sys` on `/mnt/c` under WSL). Such an entry is now skipped. The same scan runs when a session prepares a project and in `k3code setup`.
- **A turn stays on its own session's model (issue #130).** With two sessions (or a cron job, a loop or a sub-agent) on different model keys, a turn could run on the other session's main model, price and context window when that session started a turn while this one was starting up or escalating to main, and a session without a model key could get the other key stored. A turn and its sub-agents now keep the routers of their own key for the whole turn.
- **Fan-out no longer starts work its test gate cannot pass (issue #96).** The detected pytest command was `python -m pytest -q -x`, which exits 127 in the sandbox on stock Ubuntu (no `python`, and the project's venv is not active there), so every merge failed its tests, was reworked and escalated, and the parent redid the work. pytest now runs with the project's `.venv/bin/python` when there is one, else `python3`, for fan-out and the `/ultracode` final tests. Before it starts, fan-out checks that bubblewrap is usable and that a detected test command's program (for pytest: `import pytest`) is there inside the sandbox; when not, it is skipped with a notice saying why and the task runs as one turn. A configured `autonomy.fanout.test_command` is not checked.
- **`.ENV` and `~/.SSH` are credentials too (issue #133).** The sensitive-path check, the `dotenv-cat` and `ssh-key-cat` hardline rules and the redirect-target check compared names case-sensitively, so on a case-insensitive file system (a project under `/mnt/c` in WSL, macOS) `cat .ENV`, `head .Env.local`, `cat ~/.SSH/id_rsa` and the in-process `read`/`grep` of `.ENV` were allowed although they open the same files as `.env` and `~/.ssh`. Names are now compared case-insensitively everywhere; templates such as `.ENV.EXAMPLE` stay readable.

- **`grep` never returns credential files (issue #138).** An `include` glob such as `*` or `.env*` switched ripgrep's hidden-file filter off and, since rg lets the last matching glob win, also overrode the `node_modules`/`.venv` excludes, so `grep` with `include: "*"` returned `.env` lines with no prompt in any mode; the Python fallback (no rg) searched `.env` even without an include. Lines from files the sensitive-path check covers (dotenv files, `~/.ssh` and the other secret directories) are now dropped from every result and the fallback no longer opens them; the result says how many were withheld. The dependency excludes now come after `include`, so they win; `.env.example` and other templates are still searched.

- **Windows: `k3code` is a launcher, not a batch file (issue #142).** `install.ps1` wrote `k3code.cmd` and `k3.cmd`, which paste `%*` into a batch line, so cmd.exe re-parsed the arguments: `k3code -p 'explain "a && b"'` reached k3code as `explain a`, and the rest of a quoted argument after `&`, `|`, `<` or `>` ran as a Windows command (`k3code -p 'say "a & echo x> f"'` created `f`). The installer now builds `k3code.exe` and `k3.exe` from `install/k3launch.cs` with the .NET Framework compiler every Windows 10 and 11 has. They pass every argument to `wsl.exe` unchanged, call `wsl.exe` by its full path (a `wsl.exe` or `wsl.bat` in the current folder no longer runs instead), and return its exit code. A Windows without the compiler still gets the `.cmd` files, with a warning. `uninstall.ps1` removes both kinds. `scripts/ci/windows-launcher.ps1` checks the launcher on Windows.

- **`glob` and the grep fallback keep their 10 s budget (#77).** In a git work tree `glob` checked every listed file on disk before it looked at the pattern or the clock, which took minutes for a large checkout on WSL's `/mnt/c`; it now checks only its hits, and the listing stops at the time budget like the other paths. The Python grep fallback (no `rg`) reads files line by line in pieces of at most 1 MB instead of whole (a 300 MB binary took 2.6 GB of memory), checks the time budget inside a file too, and behaves like ripgrep with binary files (a NUL byte in the first 8 KB: skipped in a directory search, a single `binary file matches` line for a file named as the path) and long lines (cut to 400 columns with `[... omitted end of long line]`).
- **WSL: a Windows profile is treated like `$HOME` (issue #134).** The Windows shim starts k3code in the Linux path of the current Windows folder, so a terminal opened in `C:\Users\<name>` gave a session rooted at `/mnt/c/Users/<name>`. The sandbox bound it writable, and in auto mode `read .ssh/id_rsa`, `read AppData/.../Login Data`, `head .ssh/id_rsa`, `tar cf x .ssh` and `write .ssh/authorized_keys` or into the Startup folder were all allowed. Now, for every Windows drive WSL mounts (drvfs), compared case-insensitively as drvfs is: the drive, its `Users` folder and every profile in it (and anything above them) are refused as a sandbox root like `$HOME`, so in an interactive session each bash command needs your approval and unattended work is refused; a profile's `.ssh`, `.aws`, `.gnupg`, `AppData` and `NTUSER.DAT*` count as credentials for `read`, `grep` and bash. A project below a profile (`C:\Users\<name>\src\app`) works as before. On any system, `write` and `edit` of a file in a key store (`~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.config/k3code`, a Windows profile's keys and AppData) now ask you in every mode but yolo; writing a project's `.env` is unchanged.

They now render like prose (bold, italic, accent code, underlined link labels, math), columns still line up by visible width, and a cell that wraps keeps its style on every line.

Only a `{!cmd}` you typed is run (also on a drained queued prompt and next to a paste whose label shows one); the queue and the interrupting correction show the compact `[[ … ]]` display in the transcript again, and the gateway's span check can no longer refuse a prompt because a span ran past its text.

The first time a project asks for its state, what older versions kept under the flattened name is copied over (the old directory stays, and the TUI's input history keeps using it); projects that shared one name each get their own copy. `trust` still keys on the exact path, so a differently-cased spelling asks again.

## [0.1.0] - 2026-10-08 (alpha, not tagged)

The first version meant for people other than its author. It is alpha: the core works and is tested, but live-model behaviour, long unattended runs and multi-day use are not yet verified. The [Status section of the README](README.md#status) has the details.

### What works today

- **Coding agent.** Read, edit, patch, bash, grep, glob, web fetch and search, and todo tools. Plan mode, MCP servers, skills, project and user memory, output styles, and extra working directories.
- **Terminal UI.** An agent list under the input box with live states (working, needs input, completed, failed), focus mode, input history kept per project, slash commands with completion, and permission modes cycled with Shift+Tab.
- **Permissions.** Five modes (`default`, `accept-edits`, `plan`, `auto`, `yolo`), a hardline list that is refused in every mode, and approval rules saved per project. Bash runs in a bubblewrap sandbox in `auto`, `yolo` and background sessions when `bwrap` is available.
- **Provider routing.** An ordered chain of providers and models with error classification, cooldowns and failover. A long rate limit fails over instead of sleeping. Background work goes to cheaper tiers.
- **Reliability.** A connectivity monitor that pauses a turn while offline and resumes it by itself, retry with jittered backoff, a crash-safe journal of tool calls, a resource governor, and optional token and spend caps.
- **Autonomy.** Task scope classification, a planning turn for larger tasks, fan-out of independent parts into git worktrees with review and tests, `/goal`, `/loop`, `/ultracode` and `/ultraresearch`.
- **Automation.** Cron schedules and file, git, webhook, session, network and idle triggers, run by the daemon.
- **Learning.** A decision log, permission-rule suggestions, proposals, project preparation, and proposed changes to its own configuration, which can be A/B tested.
- **Setup and operations.** An installer for Linux and macOS, `install.ps1` for Windows (installs into WSL and adds `k3code` and `k3` commands to Windows), guided and resumable setup, `k3code doctor`, export and import bundles with secrets redacted, and an update command with rollback.
- **`k3`.** A multi-window terminal (a TUIOS fork) that shows agent states and pending approvals in its inbox.

### Not yet

- Live-model behaviour. Most exit checks use a scripted fake provider. The live-model rows ran through the `claude-cli` provider (a local Claude Code login).
- The 72-hour daemon soak. A 30-minute soak passed.
- Automatic resumption of interrupted turns in the daemon. `k3code doctor` flags unresolved journal entries.
- Platforms other than Linux on x86_64. macOS and Windows (through WSL) are untested on real machines. The installer is untested on Debian and on aarch64.
- The browser tool needs Playwright, which `presetup` installs. That path is untested on a clean machine.
- The update path against published releases. There are none yet, so the update and rollback path was only tested against local version directories.

### Changed before publication

- Hard-coded defaults that pointed at the author's own servers were replaced with neutral values. Web search has no default SearXNG instance, so the keyless DuckDuckGo fallback is used until `research.searxng_url` is set, and whenever that SearXNG is unreachable. The OmniRoute preset is no longer a default: the wizard offers Claude Code's own login when `claude` is installed, otherwise a custom endpoint. Existing configs that name it keep working. The hardline list names placeholder hosts.
- If you relied on the old defaults, set your own values in your config. To keep protecting your own hosts from remote service restarts, add patterns under `permissions.hardline`.
- Commits and uncommitted changes are checked for secrets with gitleaks (`scripts/ci/check.sh --only secrets`).

### Fixed during the long-run audit

- Redaction, install and update, and TUI and mid-turn prompt findings.
- Gateway transport and sub-agent findings, and hardening of bash, file tools, permissions and the sandbox.
- Orphan tool results that were sent to providers on the second turn of a tool-using session.
- Two daemon bugs found by an earlier soak run, and single-instance daemon handling.
- A stall in the mem0 preference writer, which blocked every session while it ran.
