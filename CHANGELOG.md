# Changelog

All notable changes are listed here. Until version 1.0, any release may change the config format, the commands or the on-disk state. Versions follow [semantic versioning](https://semver.org/) from 1.0 on.

## Unreleased

### Changed

- **CI runs locally; no GitHub Actions.** The workflows `ci.yml`, `gitleaks.yml`, `installer.yml` and `release.yml` are removed. `scripts/ci/check.sh` runs the same checks on your machine (core, tui, panes, vendor, secrets, plus shellcheck of the shell scripts), with `--quick`, `--changed` and `--only`; `--post` sets the `local-ci` commit status that branch protection on `Main` requires. `scripts/ci/merge-pr.sh` merges a pull request after a full check of its merge with `Main`, `scripts/release/release.sh` builds and publishes a release (the assets of `release.yml` plus the hashed `k3code-<version>-requirements.txt`), and `scripts/dev/install-hooks.sh` installs a pre-commit and a pre-push hook. See [`docs/RELEASING.md`](docs/RELEASING.md).
- **Look.** The default theme is hot pink (deep pink, hot pink, violet-red rules, plum fills; darker raspberry on a light terminal). Errors, success, warnings and shell mode keep their own colours. Turns are separated by a full-width rule, the status line is one continuous rule between the conversation and the input, and the agent list has a labelled header (`agents (N) · ↓ to select`).
- **Agents.** ↓ from an empty prompt moves into the agent list; Enter on a sub-agent opens its live view, Esc goes back. Finished agents leave the list after a minute.
- **Tool output.** `bash`, `grep` and `glob` results reach the model and the screen as plain text (stdout as it is; stderr, an error note and a non-zero exit code only when there is something to say), not as the Python repr of a dict with every newline and quote escaped. `write`, `edit` and plain errors are one line too (`Wrote /path`, `Edited: 1 replacement`, `Error: File not found: x`).
- **Stored sessions.** At start the daemon deletes stored sessions that never got a message, have no title or per-session setting, are not live or referenced by any loop or automation (paused ones included), and were last touched more than 30 days ago. Every `k3code agents`, `n` and abandoned TUI start used to leave one behind for good.
- **`/help`** lists the gateway's commands by category (it showed only the TUI's own commands).
- **Logging.** `k3code -p` prints only warnings by default, ends the answer with a newline and says why on stderr when a run fails. `K3CODE_LOG_LEVEL=info` brings the log back.
- **Setup.** Fast setup over an existing config puts the new provider first and keeps the others as fallbacks. `k3code doctor` reports a provider without a key as a warning while another provider can still answer.

### Added

- **Project recipes.** k3code detects every stack of a project, monorepos included (Python, Node/Deno, Go, Rust, Nix, Docker, Home Assistant, Java, Ruby, PHP, Terraform, Ansible, .NET, Make/just, CI), with the test, lint, format and build commands read from its files (nothing is run). The result is kept in `$K3CODE_HOME/projects/<project>/project.json`, not in the repository, and a changed marker file triggers a re-scan that proposes only what is new. Each stack offers opt-in proposal cards: matching skills to pin, an MCP server (a docs server; for Home Assistant its MCP endpoint, with the token named by `HASS_TOKEN`), a formatter hook after edits, exact-command allow rules for its test and lint commands, and its commands to confirm. Accepted rules, MCP servers and hooks apply to that project only. The system prompt gets a short "Project facts" section, the skills index lists the project's matching skills first, `k3code setup`/`onboard` offers the recipes (`project_recipes: accept_all|none|ask` in an answers file) and `/project` shows the stacks and pending proposals (`/project rescan` re-scans).
- **Background bash.** `bash` takes `background: true`: the command goes through the same permission decision and sandbox as any `bash` call and returns a `job_id` at once. `bash_output` returns what the job printed since the last read and whether it still runs; `bash_kill` stops its process group. Both are allowed without a prompt and reach only jobs of the calling session; a session's jobs are killed when the gateway closes it or shuts down, a sub-agent's when it finishes, and a `k3code -p` run's or REPL's when it exits. The `bash` schema documents its timeout (default 30 s, max 600 s), and a timeout says how to go on.
- **Learning from tool errors.** Tool arguments are checked against the tool's schema before the call (and before any approval prompt): the model is told what is missing or wrong and what the tool expects, instead of `Tool execution failed: 'path'`. A failure that recurs in a project (3 times in 14 days) is proposed as a project gotcha; accepted ones are kept in `$K3CODE_HOME/projects/<id>/gotchas.md` (never in the repository) and shown to the model as known pitfalls. The reason typed with a denial is kept (scrubbed), and two similar reasons for the same command become a preference proposal.
- **Loop guard on results.** The same failure three calls in a row (whatever the arguments) or two calls alternating over six calls gets one specific reminder; a main-tier turn stops after `autonomy.max_tool_errors` (default 8) failed calls in a row and lists them.

- **Agent view.** `←` on an empty input, `/agents` or `k3code agents` (on the daemon) opens a full-screen list of every session and sub-agent by state, plus earlier sessions of the current project; `session.list` rows now carry the session's `cwd`, and a `cwd` param filters the list to that project on the gateway.
- **`sandbox.home_readonly`** (user config only): `$HOME` entries that stay visible, read-only, inside the bash sandbox, for example `[".myapp"]`. The sandbox hid all of `$HOME`, so a model that checks a marker file in the home folder could never see it and repeated its first-run question in every `auto`/`yolo` session.

### Fixed

- **File modes under the daemon.** The service unit set `UMask=0077`, so every file the daemon's `write`/`edit` tools created in a project was 0600 and every new directory 0700, whatever the user's umask. The unit now uses `UMask=0022`, and a new file written by the tools gets `0666` minus the umask (the temp file behind the atomic write gave every new file 0600 too). k3code's private state no longer depends on the unit: the sessions, usage and decisions databases, the tool journals, learned notes and the setup state are made 0600 (their directories 0700) in code, existing files included; the run directory, gateway token and env file already were.
- **`k3code-recover.service`** had no hardening (`systemd-analyze security`: 9.4 UNSAFE). It now carries the daemon's `NoNewPrivileges`, `RestrictSUIDSGID`, `LockPersonality`, `RestrictRealtime` and `UMask=0022`, plus `MemoryMax=64M` and `TasksMax=16`.
- **Installer lock after a killed install.** A `SIGKILL` mid-install left `.install.lock` behind, and every later install stopped with "an install lock from pid N ..." although that process was gone. The installer now takes over a lock whose process is not running (or one that names no process and is older than 6 hours), says so, and removes the unfinished versions (no `.complete`) the killed run left. A lock whose process still runs still stops the install.
- **`k3code service uninstall`** stops `k3code-recover.service` first (a recovery unit waiting out its cooldown would start the daemon again after the uninstall), as `uninstall.sh`'s fallback already did.

- `k3code update` installed the release wheel with whatever dependency versions PyPI had that day, not the tested set. It now installs the release's hashed requirements (exported from `core/uv.lock`, published as `k3code-<version>-requirements.txt` and listed in `SHA256SUMS`) with `--require-hashes`, then the wheel with `--no-deps`. A release that lacks the requirements file is refused ("update refused ... --allow-unpinned") unless `k3code update --allow-unpinned` is given.
- An installed Playwright (the browser tool) now survives `k3code update` for release, source and git updates; every update used to build a fresh environment without it and the tool silently disappeared.
- Untrusted project content: a project's `.k3code/agents`, `.k3code/skills` and `.k3code/output-styles` load only after the project config's trust answer (a change to any of them asks again), and a project agent can no longer replace a built-in or user agent of the same name. `K3CODE.md`/`AGENTS.md` load fenced as project instructions.
- A project config can no longer set `providers`: with `base_url` and `api_key_env` it could send your key to another host. They are ignored with a warning in the trust summary and `k3code doctor`.
- Session-review facts were written into the repository's `K3CODE.md`/`AGENTS.md`. They now go to `~/.k3code/projects/<project>/learned.md`, one line of at most 200 characters each (re-applied when the file is read), and reach the prompt fenced and labelled as auto-generated. Learning scrubs secrets with the same scrubber as `/export`.
- `/export` also replaces configured key values that have no recognisable shape. `k3code import`, `/import` and the setup wizard's import ask for each MCP server, permission rule, provider endpoint and hook (`--yes` does not cover them, `--trust-bundle` does).
- The "auto-do high-risk plans" proposal needs 10 approvals and no denials in one project (it took 3, anywhere) and applies to that project only.
- **Robustness.** Every SQLite store under `$K3CODE_HOME` runs in WAL mode with a 10 s busy timeout, so the daemon, a TUI's own gateway and the CLI no longer fail with "database is locked". Files the `write` tool creates follow the umask (they were always 0600); an existing file keeps its mode. `k3code -p --json` lists the tool calls it made, and headless runs record usage. The Processes dock and collapsed pastes work (`process.list`, `paste.collapse`). A NetWatch that fails to start is logged and shown as "offline protection off" instead of silently disabling offline pause/resume; other housekeeping failures are logged too. `glob` skips `.git`, `node_modules`, `.venv`, `dist` and what `.gitignore` ignores, returns at most 1000 paths and no longer blocks the gateway; the grep fallback follows the same rules. mem0 gets each learned preference and fact once.
- **Retention.** A deleted or swept session's journal, transcript checkpoint and stored pastes are removed with it (a session id from a client never becomes a path: `session.delete` with `..` removes nothing). At start the daemon prunes usage rows older than 180 days, closed sessions' journal files older than 30 days and learning decisions older than 365 days; `/debug dump` keeps the newest 10 bundles. The limits are configurable under `retention: {usage_days, journal_days, debug_bundles, decisions_days}`.
- `k3code update` on an install made with `install.sh --from-git` (the default) failed with "no releases found on this channel": no release is published, and such an install keeps no checkout. It now looks up the newest commit of the branch or tag the install was made from (`git ls-remote`, 30 s limit, no credential prompt), reports `Already up to date.` when that commit is installed, and otherwise stages it with that commit's own `install.sh --from-git --no-activate`, then activates it as usual (smoke test, daemon restart, automatic rollback). `--check` only reports. An install pinned to a commit SHA says so. `update.url` overrides the git remote (default: the GitHub repository `update.repo`). The TUI/gateway `/update` command (and `/update now`) handles such an install the same way instead of answering "No releases on channel".
- Automations: `pause`, `resume`, `remove` and `test` by name could act on a different automation whose random id began with the same letters (`remove cafe` hit id `cafe1234`). A ref now resolves as exact id, then exact name, then a unique case-insensitive name (so `CAFE` never reaches another row's `cafe1234`), then unique id prefix with `_` and `%` taken literally; a name shared by several automations or an ambiguous prefix matches nothing. Scheduled jobs (`pause`, `resume`, `remove`) and suggestions (`dismiss`, `accept`, by title) had the same flaw and now resolve the same way; a pending suggestion is preferred over a dismissed or accepted one with the same title.
- The TUI called 29 gateway methods that did not exist, and each printed "the terminal UI and the k3code backend are out of sync": window resize, `!cmd` shell mode (and `{!cmd}` inside a prompt), `/undo` and `/retry`, `/usage`, `/status`, `/save`, `/reload`, `/reload-mcp`, `/reload-skills`, pausing and steering sub-agents, and the command catalog. They exist now. `/rollback`, `/journey`, `/plugins`, `/tools`, `/btw`, `/skin`, `/personality`, `/fast`, `/verbose` and `/replay list|load` had no backend and are removed.
- Sub-agents: finished ones showed as working, elapsed times of about 56 years, and the live view said "unavailable" for every agent.
- A loop tick could start while a user turn was still preparing, and a prompt typed behind a tick ran unattended on the cheap tier.
- Reading key files, `.env`, `~/.config/k3code` and `/proc/*/environ` is refused in every mode, and "always allow" no longer saves a command's inline `VAR=secret` in the rule.
- The credential-file refusal covers only commands that can reveal or send a file's content: readers, copies with the file as source, archives, interpreters given the path, `< file`, and `curl -d @file`, `-F name=@file`, `-T file` (the `@file` forms were let through before). Commands that only name, test or authenticate with the file get the normal decision: `ssh|scp|sftp -i KEY`, `-F CONFIG`, `-o IdentityFile=KEY`, `ssh-add`, `ssh-keygen -l|-y -f KEY`, `chmod`/`chown`/`chgrp`/`stat`/`test`/`[`/`[[`/`touch`/`realpath`/`readlink`/`ls`/`file`, `git check-ignore`, and `echo`/`printf` also into a file (not into a pipe or `$(...)`). Deleting one (`rm`, `unlink`, `shred`), `source .env`, `git add|rm|mv` of one and `docker|podman --env-file` ask a person in `default` and `auto` (an unattended run refuses them). The command in an `ssh|scp|sftp -o ProxyCommand|LocalCommand|...` value is checked like any other, glued (`-oProxyCommand=...`) or spaced, and `xargs -a FILE` (`--arg-file`) counts as reading FILE.
- The setup answer "focus mode on by default" is applied.

## [0.1.0] - 2026-10-08 (alpha, not tagged)

The first version meant for people other than its author. It is alpha: the core works and is tested, but live-model behaviour, long unattended runs and multi-day use are not yet verified. The [Status section of the README](README.md#status) has the details.

### What works today

- **Coding agent.** Read, edit, patch, bash, grep, glob, web fetch and search, and todo tools. Plan mode, MCP servers, skills, project and user memory, output styles, and extra working directories.
- **Terminal UI.** An agent list under the input box with live states (working, needs input, completed, failed), focus mode, input history kept per project, slash commands with completion, and permission modes cycled with Shift+Tab.
- **Permissions.** Five modes (`default`, `accept-edits`, `plan`, `auto`, `yolo`), a hardline list that is refused in every mode, and approval rules saved per project. Bash runs in a bubblewrap sandbox in `auto`, `yolo` and background sessions when `bwrap` is available.
- **Provider routing.** An ordered chain of providers and models with error classification, cooldowns and failover. A long rate limit fails over instead of sleeping. Background work goes to cheaper tiers.
- **Reliability.** A connectivity monitor that pauses a turn while offline and resumes it by itself, retry with jittered backoff, a crash-safe journal of tool calls, a resource governor, and optional token and spend caps.
- **Autonomy.** Task scope classification, a planning turn for larger tasks, fan-out of independent parts into git worktrees with review and tests, `/goal`, `/loop`, `/ultracode` and `/ultraresearch`.
- **Automation.** Cron schedules and file, git, webhook, session, network and idle triggers, run by the daemon.
- **Learning.** A decision log, permission-rule suggestions, proposals, project preparation, and proposed changes to its own configuration, which can be A/B tested.
- **Setup and operations.** An installer for Linux and macOS, `install.ps1` for Windows (installs into WSL and adds `k3code` and `k3` commands to Windows), guided and resumable setup, `k3code doctor`, export and import bundles with secrets redacted, and an update command with rollback.
- **`k3`.** A multi-window terminal (a TUIOS fork) that shows agent states and pending approvals in its inbox.

### Not yet

- Live-model behaviour. Most exit checks use a scripted fake provider. The live-model rows ran through the `claude-cli` provider (a local Claude Code login).
- The 72-hour daemon soak. A 30-minute soak passed.
- Automatic resumption of interrupted turns in the daemon. `k3code doctor` flags unresolved journal entries.
- Platforms other than Linux on x86_64. macOS and Windows (through WSL) are untested on real machines. The installer is untested on Debian and on aarch64.
- The browser tool needs Playwright, which `presetup` installs. That path is untested on a clean machine.
- The update path against published releases. There are none yet, so the update and rollback path was only tested against local version directories.

### Changed before publication

- Hard-coded defaults that pointed at the author's own servers were replaced with neutral values. Web search has no default SearXNG instance, so the keyless DuckDuckGo fallback is used until `research.searxng_url` is set, and whenever that SearXNG is unreachable. The OmniRoute preset is no longer a default: the wizard offers Claude Code's own login when `claude` is installed, otherwise a custom endpoint. Existing configs that name it keep working. The hardline list names placeholder hosts.
- If you relied on the old defaults, set your own values in your config. To keep protecting your own hosts from remote service restarts, add patterns under `permissions.hardline`.
- Pull requests and pushes are checked for secrets (`.github/workflows/gitleaks.yml`).

### Fixed during the long-run audit

- Redaction, install and update, and TUI and mid-turn prompt findings.
- Gateway transport and sub-agent findings, and hardening of bash, file tools, permissions and the sandbox.
- Orphan tool results that were sent to providers on the second turn of a tool-using session.
- Two daemon bugs found by an earlier soak run, and single-instance daemon handling.
- A stall in the mem0 preference writer, which blocked every session while it ran.
